# Whole-brd F3：首次普通读取与源保全观察

本目录的 F3 是 #152 的独立工程接续。它准备一个全新的私有 whole-brd，取得同次 P1/F2 原件，然后执行无内容控制与一次普通 held-FD 读取，消费完整块观察、应用对象、native getter 和健康窗口。成功状态仅为 `F3_SOURCE_PRESERVATION_OBSERVED`；`qualification=UNSUPPORTED`、production/profile/build registry 仍为空，`commit_barrier=false`。它不发 Fs、V/R/Jr，不释放 B1、M04、R05、#152 或下游 ticket。

权威范围：[F3 六文件接续](https://github.com/gbcdby/boardroom/issues/152#issuecomment-6894968776)、[SP-r2](https://github.com/gbcdby/boardroom/issues/152#issuecomment-6881600918)、[F2 有限实际接受](https://github.com/gbcdby/boardroom/issues/152#issuecomment-6893473211)。旧 F2 实例已经结束，其 boot、PID、FD 与 claim 均不转移。工程源码和纯控制通过不等于一次新的原生资格运行。

## 固定输入与构建

源码只新增 f3.py、f3-build.py、f3-run.py、f3-guest.c、本说明和 tests/whole-brd-f3.test.py。按[独立 CI 接入范围](https://github.com/gbcdby/boardroom/issues/152#issuecomment-6896141842)，database-ci 的 Linux database-tests 仅在既有 F2 后增加运行 Python F3 纯控制的三行 step。旧 F0/F0B/F2、transport、supervise、host-gate、SP native/window/diagnostics/probe 与配置均只读。

旧输入分支的构建请求只有新 run_id、base_bundle、base_bundle_sha256、brd、payload_root 五项。基础 BUNDLE 必须匹配固定 F0B 元数据，所有8项 e2fs ELF 的 size/hash、符号链接、kernel/notes/brd/BusyBox/QEMU/firmware/动态库闭包与固定环境照原合同核验；缺任一项失败，不使用系统安装版本替代。当前输入恢复状态记录在调度材料，未取得完整固定输入时不声称离线 BUNDLE 已完成。独立私有输入分支见下文。

f3-build.py 只进行离线构建：固定输入生成头文件；未修改的 SP probe.c 按其既有 gnu11/O2/Wall/Wextra/Werror 编译并仅重命名 main 符号；F3 使用原 F2 的 C11/Os 检查选项静态链接该对象。旧输入分支两条编译命令共享原10秒总预算，整个准备阶段仍60秒。BUNDLE 保存完整源码、二进制和输入摘要。

新的 CPIO 精确43项，仅比 F2 增加 mnt/f3-prepare。bin/brd-f2 这个内部分派路径刻意保留，以直接复用旧 ordinary_child 的降权、pidfd-before-ack 和真实回收实现；该成员内容及 BUNDLE kind 均明确为新 F3。旧 F2 的42项白名单没有修改。没有额外脚本、块设备成员、任意命令或可注入 guest 参数。

## 实际源码路径

新 guest 的 bootstrap 只接受 PID1/root，普通子入口只接受 UID/GID1000、parent1，原子进程身份和全能力清除由旧子 owner 与 native probe 再核。

1. 在新 boot 中先完成普通 P1、当前内核/notes/cmdline/零旧brd 原件及源代码政策 gate。随后使用固定参数加载单个64MiB brd，固定 eager mkfs 与 private mount。
2. 在 mnt/f3-prepare 写入固定非空短 payload，创建 directory、ancestor/missing 的不存在约束及固定权限/所有者/xattr。所有准备者真实 fsync、close、unmount 后才进入观察窗口。
3. 无内容控制在 mnt/brd 新 mount 上执行同次 F2 native metadata，然后执行原 SP context。之后重新 mount 执行一次原 SP ordinary；它实际打开 payload，读取真实字节，保持同一 FD 的前后 getters/path guard，并关闭所有 native handles、真实 reap 后记录 Tcut。
4. 每轮在 provider 前取得全块快照和应用对象闭包；provider 后先回读完整对象闭包，再明确执行 harness unmount，取得计数及全块快照。准备、mount 和 unmount 是 harness 行为，不称 provider commit barrier。
5. 全流程只有四次64MiB快照。失败仍沿 owned 路径尝试关闭、真实 unmount、校验本次设备节点身份后 unlink、unload；未回收 child 不冒险拆除它仍使用的资源。原错与 cleanup 错独立，无法输出最终证据也不报告成功，最终自然 poweroff 必须由 host 观察。

源观察覆盖 root、payload、directory、ancestor、lost+found；包括每个目录完整成员、每个对象完整有界 xattr、类型/owner/mode/link/size/atime/mtime/ctime、明确 absence、路径/held FD 与 close。O_PATH 元数据与带 NOATIME 的目录枚举不预热普通 payload 内容；预先离线 payload 字节从实际 inode extent 与完整块快照解析。

## 有界无损 transport 与严格消费

沿用原 serial≤8MiB、artifact≤64MiB、帧≤64KiB、2GiB child address space、既有300秒 fixture/3秒普通探针/60秒阶段上限。F3帧自身限7MiB，为原 P1/native/收尾输出留出余量；总流仍受8MiB owner 限制。没有提高预算、自动重试或删改原件。

C collector 实际 pread 全部16384个4KiB块；只有真实观察到全零的连续块才编码零游程。短读、错误、遗漏不变成零。host 拒绝 gaps、overlap、duplicate、错序、非规范零块、过界、不同设备绑定及未确认close。总解码范围≤256MiB，host只保存块摘要和有界非零字节，不落盘四个解压64MiB镜像。

实际 inode8 及 extents 决定完整4MiB journal 物理映射；四个快照的映射必须一致。应用/分配块在各观察窗口和两轮之间都必须不变。控制组不得改 journal；普通组只能出现既有 SP-r2 分类器认可的单个精确 SB 诊断事务，全部 descriptor/payload/commit/CRC、完整journal、所有 changed-device-block 原字节均核验。block0 的 SB 外字节必须在全部四张快照间逐字相同，不能让两轮内相等掩盖两轮之间的变化。

每轮挂载前的 mount-base 原始 SB，由新 guest 在准备者全部关闭且卸载以后、从同次 owned_node 约束的只读设备 FD 实际 pread 并检查 close；它是准备后的输入基线，不是构造的默认值。第一次 control 的 mount-base 通过完整协议顺序绑定到本次准备收尾，且必须与随后完整 control-before 快照的 SB 满足精确 mount 过渡；第二次 read 的 mount-base 还必须逐字等于 control-after 的卸载 SB。两轮间 write-sectors 必须不增加。

独立 harness mount 分类机制来自固定 Linux 028ef9c96e96197026887c0f092424679298aae8 的 [ext4_setup_super](https://github.com/torvalds/linux/blob/028ef9c96e96197026887c0f092424679298aae8/fs/ext4/super.c#L3096)、[ext4_update_super](https://github.com/torvalds/linux/blob/028ef9c96e96197026887c0f092424679298aae8/fs/ext4/super.c#L6206) 和 [ext4_commit_super](https://github.com/torvalds/linux/blob/028ef9c96e96197026887c0f092424679298aae8/fs/ext4/super.c#L6281)：已准备的 clean mount 只能将 mnt_count 加一、设置 needs_recovery，mtime/wtime 位于本次 mount 前后实际时钟区间，按实际 sector 计数恰好写一个4KiB SB，kbytes 在该唯一提交前保持 mount-base 值，checksum 正确；其余 SB 字节必须不变。C 仅在每次 mount 返回后增加一条只读 block-stat-mounted，仍只有四次完整快照。此处是可证伪的窄 harness 机制候选，尚非实际 Azure build 运行证明；不匹配即拒绝，不扩展 provider 诊断字段白名单或忽略额外 I/O。卸载继续使用原 SP 精确计数/时间公式；每轮原始统计和 mount-base 摘要保留在产物中。

native/window 纯消费者必须看到完整同次字节、健康 getters、owned child 正常退出、FD关闭和实际 Tcut；root UUID/FID、设备、mount、有效选项和 kernel notes 必须与本次 F2 metadata相符。控制不能含任何content，普通读取必须恰好一次且等于实际离线基线。合成控制不构造可接受 profile，也不作为原生运行原件。

## 运行边界与交付

标准 CI 和纯控制只编译/链接，或读取测试自己创建的普通临时文件；绝不启动 guest、mkfs、module、mount 或设备操作。测试里的 synthetic 明确只用于消费者约束。

实际运行必须先取得完整固定输入、新源码/二进制/BUNDLE及新claim的独立两轴审查，并由本轮总控明确释放一次执行。此源码提交本身不是运行释放。没有可用输入时应保留阻塞清单，同时完成可审工程候选。具体 CLI 仅供获准的执行者：f3-build.py --request <固定请求> --output <新目录>；之后 f3-run.py --bundle <新BUNDLE> --bundle-sha256 <精确摘要> --output <新原件目录>。不得把旧现场 FD/boot 标识复制到请求。

f3-run.py 复用原 OwnedChild/Pump/QMP、独占claim、artifact seal/close。自然 guest exit0、三路pipe EOF、owned cleanup、完整消费者和最后artifact close都确认后，调用方看到的最终结果才可保持观察成功。RESULT落盘在最终close之前，保留 final_seal_requires_caller_observation；不能将该文件单独当作最终资源已关闭证明。每一失败只保留本次失败，不重启新实例求绿。

## 私有输入的独立源码身份

新输入分支 `FIXED_F3_INPUT_CLOSURE_NOT_BOOTED` 使用公开的严格合同
`f3-inputs.json`。该文件只定义结构、角色和预算，不保存具体环境的库存、链接或
摘要。旧 F0B manifest fence、旧五字段 F3 构建分支和现有 helper 保持原合同。

公开源码的 `PRIVATE_CATALOG_SHA256` 固定为 `None`：新分支所有构建和运行入口在
输出目录、编译器、claim 或子进程创建前拒绝。请求和环境变量不能提供另一 pin、
catalog 路径或批准标记。请求仍只有 `run_id`、`input_kind`、`input_root`；私有
清单只能位于输入根的 `F3-INPUTS.private.json`，最多 64 KiB。

实际输入需要另一个经独立需求轴、标准轴和调度核定的私有源码包。它以准确公开
快照为来源，仅把上述一个 literal 改为已审私有清单摘要；其完整源码、schema、
清单和实际文件闭包形成独立身份。变更任何清单字节需要新的私有源码审查，不能
借用公开 CI 的来源身份。将任意数据及其自选摘要作为参数不构成批准。

校验保留已公开的官方 core 与固定 guest payload pins，并逐项检查实际执行路由、
大小、字节、链接拼写与完整目录成员。相同字节的另一执行路径不等于原路由。
加载器的实际 interpreter、cache、preload、私有库目录及 hwcaps 优先路径也须闭合。
固定 QEMU 的模块和固件默认搜索路径不能被 `QEMU_MODULE_DIR` 或 `-L` 隐式排除；
全部允许路径和必要 absence 都要读回。固定 kernel header、原 q35/TCG/nodefaults
参数对应绝对 BIOS 与 `linuxboot_dma.bin` 解析，只是固定机制和输入的证明。

新构建的三个编译步骤共享原 10 秒预算，准备总量仍为 60 秒。独立空工作目录需要
实际路径、身份、owner、mode 和空成员集合。运行时重新核对这些条件以及准确私有
source 和清单；失败即拒绝，已经拥有的子进程沿现有收尾流程处理。原四键环境、
stdio 参数、host gate、OwnedChild、帧、serial、artifact 和 guest 预算不扩大。
获准的新分支 runner 必须从该 BUNDLE 的固定 `runtime-cwd` 目录启动，并使用准确
绝对 BUNDLE 和输出路径；它不自动切换目录，也不接受另一个 cwd 参数。claim 与输出
保持在空目录之外。检查覆盖 claim 前、gate 前、ACK 前及真实收尾后；ACK 前出现漂移
仍回收已拥有的 gate，不启动 guest 或重试。

纯控制只使用明确的合成文件和测试源码 literal。目录、版本输出及静态模块机制
不会被解释为实际 machine、dlopen 或固件逐文件读取。实际 BUNDLE 构建、新 claim、
单次 guest、Fs/native-ext4 B1 与资格释放仍需各自准确来源的后续审查和调度放行。
