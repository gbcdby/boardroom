# Boardroom Agent 工作流程

状态：已确认（整理现有项目规则与本次用户要求）  
初版：2026-11-10；本次修订补齐检查、发布与自动推进范围

本文件保存项目跨任务的工作约定，初版依据现行 [AGENTS.md](../AGENTS.md) 与用户对自主推进、上下文沉淀和资源收尾的要求。具体目标、进度和证据保留在任务记录；本次明确要求按其范围优先。

## 资料与终点

- 项目规则、架构与正式文档：[AGENTS.md](../AGENTS.md)、[文档索引](README.md) 和 [产品架构](architecture/agent-studio.md)。
- Spec、Tickets、依赖与负责人：[GitHub Issues](https://github.com/gbcdby/boardroom/issues)，记录方式按 AGENTS.md；Boardroom 原生记录实际可用且明确切换后再迁移。
- 长期项目知识：[CONTEXT.md](../CONTEXT.md)，维护规则见 AGENTS.md 的「项目记忆」。
- 交付终点：以当前任务或 Spec 为准，区分 PR 就绪、实际合并、发布和验收；已有合并授权继续有效。

## 默认怎样推进

1. 按影响、风险与未知程度选择最短有效流程。目标清楚、影响局部且低风险的小改动直接实现、针对性检查，再走项目要求的最小独立审查和交付流程；可用现有任务或 PR 紧凑记录，不强制新建 Spec／Ticket。
2. 原因不明先做最小调查；接口、权限、迁移或关键状态变化补相关设计和验证，值得建模时再使用 TLA。未知消除后缩短流程，不按行数判定风险，不让用户反复选档。
3. 大功能或有共同约束、依赖交接的工作，先在选定权威来源创建或复用 Spec 与本批 Tickets，回读链接、验收和依赖后再分派。可以逐步设计、逐批拆票；Spec 保留概览和任务目录，聊天分工不代替共享记录，auto 也不豁免。
4. 按实际依赖、归属和写入范围推进，安全独立的工作可并行。同一 Agent 可实现并自查；可测试行为遵循 TDD，文档等使用相应检查。复用仍适用的证据，不因换技能重复检查。
5. 保留项目 CI 与独立需求、标准审查门槛；项目允许时，局部低风险小任务默认一位独立审查者分开完成两轴。再按目标推进 PR、合并或发布，阶段完成不冒充整体交付。
6. 到达目标后回写任务、依赖与 Spec 目录，沉淀可复用事实，并按既有授权清理已释放资源。

由 `deliver` 或现有总控组织，专业方法沿用当前技能和项目规则；不建立第二套任务状态。

记录写入受阻时说明具体失败及原因，保留待同步草案。继续调查、设计、有界准备或已有记录仍适用的独立任务；依赖缺失记录的新实现与分派等待补齐，不静默改用本地任务板，不绕过实际审批。恢复先核对已发生工作与真实记录，只补缺口。

| 项目约定 | 当前入口与规则 |

| 产物与发布 | 当前仓库流水线提供构建和测试报告，未配置产品发布／部署；发布目标需要另有明确任务与环境约定。 |
| 自动推进范围 | 沿用当前任务的 PR、合并等有效授权与终点；若后续配置让推送、tag 或合并触发发布，触发前核对这些效果的授权范围。 |
| 发布后检查与恢复 | 发布任务按真实产物、目标位置和验收决定检查与恢复办法；不从 CI 通过推断已经上线。 |

### CI 并行与证据保留

- Linux 数据库／SDK 与 macOS 验收独立启动；Chromium 只等待独立的浏览器依赖准备任务，不再等待 Linux 全量验收。三个既有业务检查名与验收范围保持；准备成功不代表业务验收通过。
- Linux 全量使用固定十六分片，在独立 runner 与自有 PostgreSQL 服务上并行；完整 `tests/**/*.test.ts` 发现范围不变，每分片串行执行测试文件，以隔离同一 UID 下另一测试入口与 source inventory 的并行退出窗口。按 `scripts/ci/linux-test-weights.json` 的已完成主线逐文件耗时估计，将较长文件依次分给当前累计最短分片；同值按路径和分片编号确定顺序，新增文件按一秒估计，已删除文件的旧权重不参与选择。每片保存完整发现、完整分配、所选文件和权重摘要；启动前再次核同，完整集合必须恰好覆盖一次，空分片或不一致直接失败。历史耗时仅用于调度，不代替新候选实跑或保证耗时。该调度不证明已定位或解决原 PID 的具体内核分支；被动诊断继续保留。未分片 `test:ci:linux` 仍为四文件并发，原 1200 秒执行上限、非 root 隔离及全部后续门禁不变。原 `Node 24 · SQLite / PostgreSQL` 检查聚合十六分片结果，任一失败、取消或跳过均不得通过；每分片证据有独立工件名和准确候选／发现清单，执行顺序观察不代替测试通过。
- Node 会将命令行中的路径再次解释为 glob。Linux 完整发现集中只要存在 glob 元字符或反斜杠名称，所有十六片就统一回到原完整 glob 的 Node 原生分片，记录 `selectionMode=native-glob` 及对应完整分配，避免字面路径被漏跑或跨片重复；普通路径使用 `cost-balanced`。回退可能失去均衡收益，仍必须实际满足原 1200 秒及全部失败门，不能把回退或计划本身算作通过。
- macOS 全量使用两个独立 `macos-26` runner 的 Node 原生固定分片，仍完整发现 `tests/**/*.test.ts`，每片保留原 15 分钟 job 上限、原生能力构建、native 验收、定向回归及全量默认文件并发，不启用 PostgreSQL 门控用例。分片仅写入顶层 CLI，不通过 `NODE_OPTIONS` 传给嵌套 runner；原 observer／reporter 保留，环境记录中的候选与分片、实际顶层命令及独立工件名共同绑定证据。原 `Node 24 · macOS arm64 / SQLite` 检查聚合两片，任一失败、取消、跳过或缺失结果均不得通过；历史取消仍为未完成，调度拆分不代替真实验收。
- 依赖交接仍绑定同次运行的 commit／tree、锁文件、Node／ABI、平台／架构／glibc、producer run／attempt、artifact ID 与校验和。准备失败或缺少有效产物 ID 时，既有 Chromium 检查明确失败；实际取消仍终止运行。
- 只重跑失败的 Chromium 时，消费成功 producer 输出的原 artifact ID，保留 producer 的实际 attempt，不按本次 attempt 拼工件名。依赖工件保留 1 天，过期后需连同依赖准备重新运行；诊断、报告与截图保留 7 天，不批量删除仍被交付引用的证据。
- #152 的前置定向诊断与全量测试暂时并存：它们包含不同隔离身份或串行条件，当前仍用于故障定位。只有确认原故障收口、全量日志保全及运行条件等价后，才将冗余诊断移出每次运行；不得靠删除验收、放宽超时或反复重跑掩盖失败。CI 调整与运行对照见 [#222](https://github.com/gbcdby/boardroom/issues/222)。

## 何时需要人

- 已有有效决定和授权继续适用，不逐阶段重复确认；自动模式和本文件不增加合并、发布、删除等权限。
- 能从记录、源码或实际检查查明的事自行查明。只有尚未委托、证据不能替代的人的取舍，或真实权限缺口需要交回；先完成可以自主推进的部分。
- 已有预算、停点与无进展处理约定继续适用；缺口只阻塞受影响工作，不因一次失败扩大成全局暂停。
- 想主动参与大功能前期方向时，可调用 `challenge`，分批讨论关键取舍并保存到共享记录；这不是自动流程的必经阶段，Agent 不自行启动人工入口。

## 汇报、暂停与恢复

- 用简短白话先说结果、影响和必要决定；适合比较或解释关系时用小表、图。详细证据保留链接，不要求人逐条阅读 Agent 对话。
- 自然语言暂停、纠正和改向直接有效。记录已完成效果、在途或未知结果及接续点；恢复先查当前事实，避免重复动作。
- 是否能跨会话、后台运行或唤醒，由真实宿主能力决定；没有执行者时保留交接，不宣称正在持续运行。

## 知识与资源收尾

- 长期知识只保存难以重新发现、后续会用到的项目事实，注明范围、日期和来源；已有正式归属就引用，无新事实不写。
- 清理只涉及本次已释放的临时分支、专属 worktree 和可丢弃材料。按已有授权执行并回读，保留脏目录、未交付内容、共享或活跃资源和仍被依赖的产物；无授权时交回具体清单。
