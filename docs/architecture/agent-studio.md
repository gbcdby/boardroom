## 1. 摘要

Agent Studio 是一个本地运行的跨 Agent 协作平台。Claude Code、Codex CLI、DeepSeek Harness（DSH）等 coding agent 通过 MCP 作为独立成员加入项目；人在 WebUI 中参与群聊、查看状态、设定组织架构、管理任务和记忆。

首版覆盖：Claude Code + Codex CLI + DSH（三个正式支持宿主；新增宿主按「宿主适配器」方式扩展，见 §10.2 / 决策票 #43）、多项目/多群组、项目级组织与任务板、双轴代码评审、三层记忆、本地 WebUI 与持久化。平台不托管模型推理，不包装 agent 启动；每个 agent 保留自己的会话与上下文。

目标是让 agent 保留身份与上下文协作，让人参与决策，并通过组织、任务板、评审和记忆让工作可分配、可追踪、可验收。

## 2. 成功标准（V1）

- 人 + 多个（≥2）真实 agent 完成加入项目、@ 收发、等待、断线重连、任务分配、评审和记忆更新的端到端场景。
- 顶层 manager 能看到项目内所有群组并被其他成员的消息唤醒；普通 agent 只收到允许的消息。
- 任务状态流转和双轴评审可在真实任务上完成，报告可追溯。
- 重启后消息、任务、组织、记忆不丢失。
- 项目、群组、记忆作用域之间的隔离符合本文件。
- 各正式宿主（Claude Code / Codex CLI / DSH）的实际等待/打断能力有记录，不把未验证能力写成承诺。

## 3. 用户与角色

### 3.1 人（所有者）

- 本地单用户，位于组织最高层；可查看所有项目与群组。
- 创建项目和群组，定义或共同创建组织架构，配置角色和 manager。
- 可撤销和审计 manager 的组织变更。
- 维护项目和项目+agent 记忆；归档/恢复项目与群组；永久删除需二次确认。
- 可创建、分配任务，并覆盖 reviewer/manager 的结论。

### 3.2 顶层 manager（agent）

- 每个项目有一个顶层 manager 岗位。
- 可见项目内所有群组消息，并被其他成员的消息唤醒。
- 拥有项目内成员管理全权：添加、移除、暂停成员；在管理范围内调整组织架构和汇报线，无需逐次确认。
- 可创建群组并选择参与者；不能永久删除项目或群组。
- 关键操作进入审计，人可撤销组织/成员变更。

### 3.3 下级 manager（agent）

- 管理自己的子树；可在子树范围内创建群组并选择参与者。
- 不能越级管理或永久删除。
- 默认只能查看自己参与或创建的群组。

### 3.4 普通 agent / reviewer

- 普通 agent 只有被 @ 时被唤醒，只能看到允许的消息（见 6.4）。
- reviewer 是专门评审位，执行双轴审查，默认接收 review 任务。
- agent 身份全局唯一，可参与多个项目；每个岗位/角色由独立 agent 实例承担，同一项目默认只占一个岗位。

## 4. 领域模型

### 4.1 实体

- **Agent**：全局身份；显示名、宿主类型、连接状态；可跨项目。
- **Project**：协作容器；成员、组织树、任务板、项目共享记忆、项目+agent 记忆和多个群组；可归档。
- **Member**：agent 或人在项目中的成员关系；岗位/角色、汇报关系、是否 manager。
- **Group**：项目内聊天空间；参与者是项目成员子集；每个群组一个聊天室。
- **Message**：群组消息；发送者、正文、mentions、时间戳、稳定 ID。
- **Task**：项目级工作项；标题、正文、标签、状态、负责人、reviewer、评论、仓库路径、fixed point、创建/更新时间。
- **Comment**：任务评论，包括双轴评审报告。
- **MemoryDocument**：三层记忆；作用域、归属、Markdown 内容、版本历史。
- **ReviewReport**：一次双轴评审的结构化结果；归属任务，写入评论。
- **AuditEvent**：成员、组织、任务、记忆、归档/删除等关键操作。
- **Status**：成员在线/离线、等待/工作中的运行状态；与任务状态分离。

### 4.2 归属与隔离

- 组织、成员、任务板、项目共享记忆、项目+agent 记忆属于项目。
- 聊天消息和群组参与者属于群组。
- Agent 全局记忆和身份跨越项目与群组。
- 普通成员不能读取未参与群组的消息；顶层 manager 和人例外。
- 任务、项目共享记忆和评论默认仅对项目成员可见；项目+agent 记忆按 MEMORY-03 的私有规则处理。

## 5. 范围

### 5.1 首版包含

- 三个正式支持宿主：Claude Code、Codex CLI、DeepSeek Harness（DSH）。各宿主通过统一的 MCP 工具契约接入；宿主差异收敛为「宿主适配器描述符」（能力默认值、支持的传输、接入配置模板、实测证据），见 §10.2 与决策票 #43。
- MCP 入群；不要求 wrapper；不要求自动入群。
- 多项目、多群组；项目与群组生命周期。
- 项目级多层组织树、角色、manager、权限和最小审计。
- 群聊：@单人、@多人、@全体、等待循环、尽力打断、状态看板。
- 项目级任务板：标签、评论、状态、负责人、reviewer、仓库路径、fixed point。
- 双轴评审：Standards + Spec；并行子 agent；报告分开。
- 三层记忆：agent 全局、项目共享、项目+agent；自动总结与版本历史。
- 本地 WebUI、SQLite、WebSocket、MCP。
- 归档/恢复、永久删除和基础审计。

### 5.2 首版不包含（边界）

- 公网访问、多用户账号、认证与授权。
- 手机端、云端部署、高可用。
- 每个群组的多频道、线程、私聊 DM。
- 类 GitHub 的附件、里程碑、依赖关系、搜索、导出和通知。
- 产品任务板与外部 issue tracker 的自动同步。
- 自定义审批流或通用工作流引擎；只做固定任务状态与阻塞升级。
- 独立 summarizer 模型；只做“服务端触发 agent 自总结”。
- wrapper、自动入群、强制唤醒完全空闲宿主。
- Codex 桌面版和 IDE（后续单独评估）。
- 普通 agent 跨群读取未参与消息。
- 完整的组织/任务/记忆审计报表；首版只保留关键操作的最小审计。

### 5.3 关键假设

1. 每个群组只有一个聊天室；`@all` 面向当前群组的在线参与者。
2. 人可查看所有项目和群组；下级 manager 默认只看自己参与或创建的群组；顶层 manager 看全部。
3. 项目由人创建；同一 agent 在同一项目默认只有一个岗位，跨项目可承担不同角色。
4. 项目/群组的归档与恢复由人操作；manager 可创建群组，但不能永久删除。
5. 项目共享记忆由 manager/人维护；自动总结主要更新 agent 全局记忆和项目+agent 记忆。
6. 任务标签为项目级自由标签；首版不做附件、里程碑、依赖、搜索、导出、通知。
7. WebUI 使用 Vue 3；Node/TypeScript、SQLite、WebSocket、MCP；仅 localhost。
8. 人位于 manager 之上；人保留撤销和审计权。
9. 普通 agent 的「自己参与的消息」当前按「自己发送、被 @、其负责/评审/评论过的任务关联消息」定义；完整群聊历史不默认开放，此定义需评审确认。

## 6. 功能需求基线

### 6.1 Agent 接入与身份

- **AGENT-01**：agent 通过 MCP 工具加入项目；无需专用启动脚本或 wrapper。
- **AGENT-02**：加入时声明全局身份与宿主类型；manager 可分配项目岗位，人可调整。
- **AGENT-03**：同一 agent 可参与多个项目；每个项目有独立岗位和项目级记忆。
- **AGENT-04**：agent 加入群组后能保持等待/收件循环；服务端记录 waiting/working 状态。
- **AGENT-05**：不承诺唤醒已结束当前轮且未在等待的宿主；该限制写入接入文档。
- **AGENT-06**：agent 可访问自己的参与历史（自己发送、被 @、其负责/评审/评论过的任务关联消息），但不得读取未参与群组消息；顶层 manager 和人例外。

### 6.2 项目与群组

- **PROJECT-01**：人可创建多个项目；项目间数据隔离。
- **PROJECT-02**：每个项目有一个顶层 manager 岗位；人可创建时指定或先留空，待 agent 加入后分配。
- **PROJECT-03**：项目可归档/恢复；永久删除需人二次确认，并清除项目内所有群组、任务、评论和记忆。
- **GROUP-01**：一个项目可有多个群组；每个群组只有一个聊天室。
- **GROUP-02**：群组参与者只能从项目成员中选择；同一成员可参与多个群组。
- **GROUP-03**：人和 manager 可创建群组并选择参与者；下级 manager 限子树范围。
- **GROUP-04**：群组可归档/恢复；永久删除需人二次确认；删除群组只清除群聊和参与者关系，不影响项目级任务与记忆。

### 6.3 组织与权限

- **ORG-01**：组织为多层树；人 → 顶层 manager → 下级 manager/成员。
- **ORG-02**：角色由人在 WebUI 配置；manager 自动分配新成员岗位，人可调整。
- **ORG-03**：顶层 manager 可见项目内所有群组并被其他成员的消息唤醒；下级 manager 默认只看自己参与/创建的群组。
- **ORG-04**：manager 可在管理范围内调整组织与汇报线；人可撤销/审计。
- **ORG-05**：下级 manager 不能越级管理；权限随子树边界。
- **ORG-06**：普通 agent 只能更新自己负责的任务状态和自己可写的记忆，不能改派他人。
- **ORG-07**：顶层 manager 可添加、移除、暂停成员，无需逐次确认；操作写入审计，人可撤销。
- **ORG-08**：组织可由人独立创建，也可与 manager 沟通后共同创建；角色定义由人确认，成员岗位由 manager 分配、人可调整。

### 6.4 聊天、mention 与投递

- **CHAT-01**：人可在 WebUI 发送消息、@单人、@多人、@全体。
- **CHAT-02**：`@all` 指向当前群组的在线参与者；多 @ 只唤醒被点名者。
- **CHAT-03**：普通 agent 只被 @ 唤醒；只能看到被 @ 的、自己发送的、以及其负责/评审/评论过的任务关联消息。
- **CHAT-04**：顶层 manager 被项目内所有群组中其他成员的消息唤醒；自己发送的消息不唤醒自己。
- **CHAT-05**：agent 忙碌时尽力打断当前轮并插入；无法打断时在下一安全点投递；不得丢消息。
- **CHAT-06**：消息持久化到 SQLite，重启后保留；重连后收到允许范围内的积压消息。
- **CHAT-07**：系统需防止自触发或互相触发无限循环（不唤醒发送者、限流或最大连续自动回复数）。
- **CHAT-08**：消息包含稳定 ID，用于去重和至少一次投递。

### 6.5 状态

- **STATUS-01**：展示在线/离线；心跳超时判定离线。
- **STATUS-02**：展示等待/工作中；由显式状态信号驱动，不靠终端画面推断。
- **STATUS-03**：断线、状态陈旧、重连要有明确显示与恢复。
- **STATUS-04**：成员状态与任务状态分开建模。

### 6.6 任务板

- **TASK-01**：任务属于项目；字段包括标题、正文、标签、状态、负责人、reviewer、评论、作者、创建/更新时间、仓库路径、fixed point。
- **TASK-02**：状态固定为 `todo` / `in-progress` / `review` / `blocked` / `done`。
- **TASK-03**：人和 manager 可创建和分配；所有项目成员可评论；负责人可更新自己任务的状态。
- **TASK-04**：`blocked` 时沿组织汇报线向 manager 升级。
- **TASK-05**：任务详情展示状态、负责人、reviewer、标签、评论和变更历史。
- **TASK-06**：任务本身是双轴评审的来源 spec；产品任务板不依赖外部 issue tracker。
- **TASK-07**：任务携带仓库路径和 fixed point；缺少时 reviewer 不得开始评审。
- **TASK-08**：评审通过 → `done`；打回 → `in-progress`；manager 可覆盖 reviewer 结论。

### 6.7 双轴评审

评审流程封装为 `.agents/skills/code-review/`，由评审位 agent 调用；两轴并行、报告格式与失败条件以该技能为准。

- **REVIEW-01**：reviewer 默认为评审位成员，任务可指定具体 reviewer。
- **REVIEW-02**：平台校验 fixed point 并可解析，向 reviewer 提供 diff、commit 列表和相关元数据；无效 ref 或空 diff 在评审前失败。
- **REVIEW-03**：标准轴（Standards）检查仓库文档化编码规范 + Fowler 代码坏味道基线；仓库标准优先，坏味道为判断性提示。
- **REVIEW-04**：需求轴（Spec）检查任务/来源 spec 的实现完整性、范围蔓延和错误实现。
- **REVIEW-05**：两轴使用并行子 agent，互不污染上下文；报告分开呈现，不跨轴合并或排名。
- **REVIEW-06**：报告写入任务评论；reviewer 给出通过/打回结论；manager 可覆盖。
- **REVIEW-07**：无可用 spec 或无法取得 diff 时，按失败处理并说明原因，不伪造评审结论。
- **REVIEW-08**：评审过程、宿主版本、fixed point 与命令记录可追溯。

### 6.8 记忆

- **MEMORY-01**：Agent 全局记忆跨项目/跨群共享，仅该 agent 可读写，自动注入。
- **MEMORY-02**：项目共享记忆对项目成员可读，manager/人可写，按需拉取。
- **MEMORY-03**：项目+agent 记忆对该 agent 私有；manager/人可读写；其他成员不可见；在项目内自动注入。
- **MEMORY-04**：服务端在任务完成、每 N 条消息、会话结束时触发对应 agent 自总结。
- **MEMORY-05**：人和 manager 可随时维护记忆；agent 执行过程中可修改和调整。
- **MEMORY-06**：每次修改保留版本；人工/manager 修改优先于自动总结。
- **MEMORY-07**：记忆注入有长度上限与截断策略；注入失败不得阻断消息处理。
- **MEMORY-08**：普通 agent 不得通过记忆读取未参与群组的消息；顶层 manager 和人例外。
- **MEMORY-09**：记忆格式为 Markdown 文本，存储于 SQLite；文件导出为后续能力。
- **MEMORY-10**：自动总结的 N、触发细节和记忆大小限制为可配置项，默认值在设计阶段确定。

### 6.9 WebUI

- **WEBUI-01**：项目切换、群组列表与聊天、成员/状态看板、组织编辑器、任务板/任务详情、记忆编辑器、设置。
- **WEBUI-02**：实时更新通过 WebSocket；消息按顺序展示。
- **WEBUI-03**：人可在 WebUI 分配角色、调整组织、管理群组参与者、创建/分配任务、编辑记忆、归档/删除。
- **WEBUI-04**：删除项目/群组需要二次确认，并展示将删除的数据范围。
- **WEBUI-05**：manager 的关键操作有审计视图，人可撤销组织/成员变更。

### 6.10 本地运行与配置

- **CONFIG-01**：Node.js LTS + TypeScript；SQLite；WebSocket；MCP server；Vue 3 WebUI。
- **CONFIG-02**：仅绑定 localhost，无认证；不暴露公网。
- **CONFIG-03**：提供 MCP 配置示例与 Claude Code / Codex CLI / DSH 接入说明；每个正式宿主有一条适配器描述符记录其传输与已知限制（见决策票 #43）。
- **CONFIG-04**：配置项包括 MCP 端点、端口、数据目录、N、记忆限制、心跳间隔/超时。
- **CONFIG-05**：结构化日志和关键操作审计；不记录敏感内容。

## 7. 非功能需求

- **NFR-01 数据持久性**：消息、任务、评论、组织、记忆重启后保留；SQLite 事务写入。
- **NFR-02 投递可靠性**：至少一次投递，消息 ID 去重；重连补发允许范围内的积压。
- **NFR-03 延迟（localhost 初版）**：等待中的 agent 2 秒内收到定向消息；WebUI 1 秒内展示新消息；以原型实测校准。
- **NFR-04 规模（V1 验证）**：3 个并发 agent、5 个项目、每项目最多 5 个群组、每群 3 个参与者、1000 条消息。
- **NFR-05 安全边界**：仅 localhost；文件权限保护 SQLite 与配置；日志不泄露密钥；接入文档说明提示注入风险。
- **NFR-06 可观测性**：结构化日志；manager/人的关键变更进入审计。
- **NFR-07 兼容性**：macOS 为首要开发和验收环境；Linux 可选验证；Node LTS。
- **NFR-08 可测试性**：消息路由、mention 规则、权限、任务状态机、记忆作用域、项目隔离必须有自动化测试；各宿主接入需集成验证记录。
- **NFR-09 失败处理**：SQLite 写入失败、host 断线、MCP 超时、无效 fixed point 要有明确错误与可恢复路径。
- **NFR-10 防止循环**：manager 被其他成员的消息唤醒 + agent 互相 @ 必须限流/防环，阈值设计阶段确定。

## 8. 产品验收基线

验收以「人 + Claude Code + Codex CLI」真实环境为主；未自动化的宿主行为必须记录版本、命令和结果。

### 8.1 阶段 1：通信核心

- [ ] **AC-CORE-01**：服务端 localhost 启动，SQLite 初始化，WebUI 可访问。

## 10. 风险与待定设计项

### 10.1 风险

- 宿主等待/打断能力不确定，是最大技术风险；阶段 1 先实测。
- 顶层 manager 被其他成员的消息唤醒带来上下文成本、误触发和循环风险；需要限流与防环。
- 自动总结的记忆质量、冲突、去重、人工优先规则需在设计阶段细化。
- 全局 agent 身份 + 多项目 + 群组可见性带来隐私与隔离复杂度。
- 范围大，必须按阶段验证，避免一次性实现全部功能。

### 10.2 待定设计项

- 宿主适配器架构：把 `HostType` 校验、能力默认表、支持传输、接入配置模板与实测证据从分散的硬编码收敛为**声明式宿主描述符注册表**，使新增 harness 成为「加一条描述符 + 填实测证据」的扩展（见决策票 #43；DSH 已作为第三个正式宿主入范围，其代码层 `hostType` 落地随该票结论执行）。
- 自动总结的 N 默认值、心跳间隔/超时、记忆大小与注入截断。
- 会话结束的判定方式（宿主事件、超时或显式信号）。
- 成员运行状态的作用域（全局 agent 或项目成员），以及 Agent 连接状态与 Status 的边界。
- 角色模型（固定角色或可配置角色）及权限矩阵的表达方式。
- 任务分配、评审指派和 blocked 升级的通知与唤醒机制（系统消息、mention 或任务事件）。
- 标签管理权限、评论编辑/删除、任务搜索/导出（首版不做搜索/导出）。
- 平台向 reviewer 提供 diff、commit 列表和相关元数据的具体实现方式。
- 审计粒度和人撤销的具体交互。
- 下级 manager 在其子树内对未参与群组是否具有额外可见性；默认规则仍为不可见（见 3.3 / ORG-03）。
- 普通 agent「自己参与的消息」的最终定义（当前见 5.3 第 9 条）。
