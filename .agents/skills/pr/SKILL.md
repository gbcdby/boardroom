# PR 描述

## 调用方式

可由 agent 在 `code-review` 后自动调用。评审已通过时创建 **ready PR**；评审尚未完成时创建 **draft PR**。合并到默认分支由用户决定，不自动合并。

## 目标

让评审者在一屏内看清三件事：改了什么、证据是什么、合并风险有多大。PR 描述是交付说明，不是过程日志，也不是双轴审查报告的副本。

## 前置条件

- 变更已实现，且能给出 fixed point 和 diff。
- 已取得 `code-review` 的结论，或明确知道尚未评审；尚未评审时，PR 中只能标注「待评审」，不得写「已通过」。
- 已知所属 ticket 和来源 spec 的链接。
- 用户已启动实现/评审流程，或明确要求准备 PR；未授权创建时只生成描述，不创建 PR。

## 流程

1. 收集输入：diff、提交列表、ticket、来源 spec、双轴审查结论、验证记录。
2. 写摘要：选择能说明问题的**最小视图**，不要复述整份 diff。
3. 写证据：给出修改前后的真实结果；涉及宿主能力时写明命令、宿主版本和未验证项。
4. 写合并风险：判断单向门/双向门，说明影响半径、回滚方式和数据迁移。
5. 写关联：ticket、spec、双轴审查报告的位置。
6. 用项目语言和领域术语表述；保持简短。
7. 发布：平台支持 CLI/API 且用户已授权时，用模板创建 PR——评审已通过创建 ready PR，尚未完成评审创建 draft PR；否则输出完整描述，交由用户创建。创建后不要自动合并、force-push 或关闭 issue。

## 模板

```markdown
## 摘要

<最小视图：伪代码 / 调用树 / 文件树 / Mermaid / diff；
只保留支撑本次变更的部分>

## 证据

- 修改前：<失败测试 / 旧行为 / 截图>
- 修改后：<通过测试 / 新行为 / 截图>
- 验证命令与宿主版本：...
- 未验证项：<没有就写「无」>

## 合并风险

- 门类型：单向门 / 双向门
- 影响半径：<单一模块 / 数据 / 协议 / 权限 / UI>
- 回滚方式：...
- 数据迁移：<有/无；是否可逆>

## 关联

- Ticket: #N（由 `implement` / `implement-spec` 在评审通过后关闭，PR 不负责关闭）
- 来源 spec: #M
- 双轴审查：标准轴 ✅/❌；需求轴 ✅/❌（报告见评论）
```

## 摘要视图选择

选最小、最能说明问题的一种或几种，不要求全部使用：

- 逻辑或算法：伪代码。
- 运行控制流：调用树。
- UI 结构：组件树，标出关键状态和模块边界。
- 文件职责或大范围重构：浅层文件树。
- 组件交互或数据流：Mermaid。
- 变更本身是重点：diff。

只保留回答问题所需的调用、文件、状态和边界；小改动用纯文字说明即可。

## 合并风险

- **单向门**：难以回滚的变更。例如 SQLite 数据迁移、MCP/宿主协议变更、删除或审计逻辑、权限与可见性规则。
- **双向门**：可以低成本回滚的变更。例如局部 UI 调整、纯内部重构。
- 影响半径写清范围：单模块、共享类型、持久化数据、跨宿主协议、WebUI。
- 有数据迁移时写明是否可逆、失败时如何恢复；没有迁移时写「无」。

## 规则

- 没有评审结论时，不写「已通过」；可以写「待评审」并说明缺失原因。
- 双轴报告放在评论或链接中，PR 正文只写结论和位置。
- 未实测的宿主能力单独列为「未验证项」，不混入证据。
- 不写过程性内容：不记录访谈、调试流水账或临时决策。
- 证据必须真实；测试未通过时如实说明，不伪造结果。
- 评审通过时创建 ready PR；待评审时创建 draft PR。
- 合并到默认分支由用户决定；不自动合并、不自动 force-push。

## 反模式

- 用大段流水账代替摘要。
- 只有修改后的截图或输出，没有修改前。
- 把双轴报告全文粘进 PR 正文。
- 把未验证的宿主行为写成已验证。
- 忽略数据迁移、回滚和兼容性。
- 在没有评审结论时宣称「已通过」并请求合并。
