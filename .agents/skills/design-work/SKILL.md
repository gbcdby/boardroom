# 行为与系统设计

设计足以指导实现、能够被验证、也能让人理解的方案。把精力用于真实的不确定性和会影响后续工作的边界。

## 职责与输入

- 读取当前目标、验收条件、项目约定、现有架构、源码及已确认决定。没有完整规格时先补与当前设计有关的最小信息。
- 先确认用户要求设计到哪里。设计交接结束后返回调用者；外层已授权的实现任务可以继续，但本 Skill 不自动接管它。
- 保持业务语言、验证工具和协作宿主解耦。没有 boardroom、Matt 或 pstack 也能完成本工作。
- 可在既有权限和预算内开展研究、隔离原型与测量。原型标明用途、范围和清理方式，不把实验代码悄悄写成生产实现。

## 1. 固定设计对象和既有边界

1. 确认设计对象的版本和范围，读取与它相关的调用方、状态所有者、数据持久化和外部效果路径。
2. 区分当前实现、拟议设计和已经接受的架构基线。设计文档不能把尚未实现的能力画成当前能力。
3. 把用户目标连接到稳定的验收条件；记录前提、环境限制和未知，而不是从现有代码反推所有需求。
4. 复用已有决定及其适用条件。事实发生变化时保留原决定与替代关系，不通过改写历史隐藏设计转向。
5. 说明本次变化需要解决的问题。若只需一个局部改动，不强制多方案、长文档、架构图或 ADR。

## 2. 设计可观察行为

从用户或调用者的入口开始，明确输入、成功结果、失败结果和未知结果。

- 写出主路径、必要的异常路径、取消与恢复行为，以及兼容性承诺。
- 对有状态行为明确状态、事件、转移条件和终态；区分用户请求、系统接受与效果真正提交的时刻。
- 对重试说明操作身份、重复效果和超时后未知结果的处理；对并发说明谁拥有决定权和冲突如何解决。
- 用稳定编号表达必须成立的性质；分清业务约定、环境假设、实现义务和可自由选择的机制。
- 对 UI 或交互不确定性优先使用可操作原型；对简单条件使用决策表；只有状态关系有解释价值时才绘图。

把可以由证据回答的问题交给研究和实验。涉及产品承诺或价值取舍时，先准备具体选项、影响和推荐，再按项目已有决定流程处理。

## 3. 设计模块与演进方式

形成最小架构差异，至少回答与本次变化相关的问题：

| 设计面 | 需要回答 |
| --- | --- |
| 职责 | 哪个模块负责判断、执行、保存和观察 |
| 状态 | 谁拥有状态，谁能写，失败后哪个事实仍可信 |
| 接口 | 输入输出、错误、版本兼容、调用者可依赖的承诺 |
| 依赖 | 哪些代码、配置、事件格式或运行环境需要一起改变 |
| 演进 | 如何部署兼容变化，何时移除旧路径，如何恢复或补偿 |

优先把稳定承诺放在清楚的接口上；内部实现保留适当自由。不要把某数据库、队列或锁写成无依据的强制要求。

只有存在实质取舍时比较少量结构不同的方案。分别记录收益、代价、失败方式、可逆性和待验证假设，不用模型多数票代替依据。

## 4. 在实现前建立验证路径

1. 对每项关键验收条件指定检查方式、输入条件、可观察输出和失败判据。
2. 判断需要的操作面是否真实可用：CLI、API、浏览器、设备、测试环境或其他项目工具。缺口写成具体前提，不能默认某个 harness 一定具有能力。
3. 选择能揭示核心风险的小型纵向实验；实验结果绑定实际对象、环境和操作，不用伪造示例代替运行。
4. 将并发交错、幂等、乱序、资源竞争、取消或恢复等适合建模的问题整理为形式化输入；没有这些风险时不强制建模。
5. 如需形式化验证，把明确性质和假设交给独立的 `tla-verify-design` 或适合的验证者；没有该 Skill 时交付同等输入，不假称已经运行 TLC。
6. 保留模型结论、源码对应核验和实际行为证据的不同状态。模型通过不授权实现合并，也不表示所有语言级风险已检查。

## 5. 提供人能理解的视图

按 [可读视图与语义](references/visual-semantics.md) 把行为与架构投影为最有用的图或表。

- 默认突出本次变化、关键不变量、异常路径及尚未确定的行为。
- 把节点、转移或接口关联到契约与证据；图仅是阅读视图，不能取代这些权威记录。
- 标记抽象、隐藏转移和检查范围。不要为了简洁合并会改变判断的状态或丢掉反例路径。
- 把反例解释成简短的事件顺序、违反的承诺及修改后的义务；不以图中颜色表示整个实现已经证明。
- 保留相对已接受基线的累计架构差异；“上次看过”与“已经接受”是不同记录。

## 6. 交接并结束本职责

交接足以让接收者独立行动：目标、行为契约、架构差异、决定依据、实施义务、验证路径、尚未解决的问题和返回设计的条件。

使用 `schema_version: work-result/v1`：`work_id`、`skill`、`outcome`、`subject`、`evidence`、`unresolved`、`changed_assumptions`、`next_action`。`subject` 至少包含 `kind` 和真实 `id`，按需补 `base_id`、`contract_id`、`environment_id`、`worktree_digest`；证据保留原状态、提供者、版本和适用范围。

- **COMPLETE**：约定范围内的设计产物与实施义务已明确；列明未执行的验证，不暗示方案已实测。
- **INCONCLUSIVE**：现有实验或证据不足以选择关键方案；给出最有价值的下一项调查。
- **BLOCKED**：关键决定或必要访问缺失；继续完成不依赖该项的设计工作，再交回具体阻塞。
- **NOT_RUN**：检查仅有计划尚未执行。`PASS` 只用于有明确范围和证据的检查，保留 TLC 等工具的原始状态。

若后续发现调用语义、原子性、状态归属、外部效果、环境假设或兼容承诺改变，重新评估受影响的设计和证据。图形样式变化仅重评投影；语义变化不能靠重画图更新“已验证”状态。

静态源码事实使用 `status: OBSERVED` 与 `kind: source_inspection`；引用旧实测使用 `HISTORICAL` 并保留其对象与日期。证据可记录 `id`、`locator`、`scope`、`status`、`producer`、`subject_id`，不把静态或历史证据标为当前实测 `PASS`。

JSON 交接时，next_action 与 evidence.scope 使用非空文本，结构化详情另放扩展字段；subject.id 使用含真实版本的不可变身份。引用不同对象的原始材料时保留原 subject_id 并标 relation=background，直接结论绑定当前对象；独立工具的原报告原样保留，由交接层包装，不要求它改用本格式。
