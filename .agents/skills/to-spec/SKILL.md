# 产品 Spec 编写

## 调用方式

本技能由用户显式触发。完成后提示用户下一步（通常是 `to-tickets`）；不要自动拆分任务或调用其他用户显式触发的技能。

## 目标

把已确认的需求固化为一份长期有效的正式 spec。spec 必须足以支撑评审、拆分任务和验收，不负责继续访谈，也不擅自补充用户没有确认的需求。

## 主 spec 与子 spec

- 主 spec 描述产品级范围、边界和整体验收；子 spec 细化一个阶段或模块。
- 只允许一层父子关系：主 spec → 子 spec → ticket。
- 创建子 spec 时，输入是已确认的父 spec 加明确的需求子集；仍需用户确认子 spec 本身。
- 子 spec 必须：
  - 在元数据中声明父 spec；
  - 只细化父 spec 中已有的需求，不新增或改变范围；
  - 映射父 spec 的需求 ID 与验收 ID；
  - 维护自己的 ticket 列表。
- 需要改变范围时，先更新父 spec，再更新子 spec。
- 主 spec 维护子 spec 列表；子 spec 关闭后，主 spec 继续活跃；主 spec 在所有子 spec 和 ticket 完成后才关闭。

## 项目适配

本技能默认使用下列约定；宿主项目有不同规范时，以宿主项目为准：

| 用途 | 默认约定 | 说明 |
| --- | --- | --- |
| agent 约定 | `AGENTS.md`、`CLAUDE.md` 或等价文件 | 先读其中的流程与边界要求 |
| 项目约定 | `AGENTS.md` 或项目约定 | 决定 spec 的发布与状态更新方式 |
| 正式 spec | issue tracker | 本技能的产出位置 |
| spec 层级 | 主 spec + 一层子 spec | 子 spec 声明父 spec；主 spec 维护子 spec 列表 |
| 任务跟踪 | issue tracker 或项目管理工具 | 任务拆分由 `to-tickets` 技能执行，不在本技能内完成 |
| 临时输出 | `.agent-output/` 或项目约定目录 | 存放草稿与过程材料 |
| 文档语言 | 项目约定语言；无约定时跟随用户语言 | 本仓库使用中文 |

本项目使用 GitHub Issues：正式 spec 直接创建为 issue。

### 标签约定（项目适配）

| 标签 | 含义 | 用在哪 |
| --- | --- | --- |
| `needs-info` | 等人补充信息或做决定 | spec 草案、被外部事实阻塞的票 |
| `ready-for-agent` | 规格完整，agent 可直接接手 | 只给 ticket |
| `ready-for-human` | 需要人评审、裁决、合并或实测 | 待评审的 ticket |
| `wontfix` | 不做 | 已取代、已放弃、被否决；同时关闭 |

规则：

- 每个开放 issue 最多一个就绪标签；没有就绪标签表示当前没有待办。
- spec 永不打 `ready-for-agent`。
- 不使用 `in-progress`、`phase:*`、`type:*` 标签。
- 标签缺失时先创建再使用。

其他技能使用的专属标签不在此列，各自维护。

### 标题前缀（项目适配）

| 前缀 | 对象 |
| --- | --- |
| `[主 spec]` | 主 spec |
| `[子 spec]` | 子 spec |
| `[ticket]` | ticket |

检索时使用完整方括号前缀（`in:title "[子 spec]"`），不要只写 `spec`。ticket 的短号（`T1`、`F1`）放在前缀之后，区分基础票与纵向切片票。

宿主项目使用其他标签字符串时，在本表中替换为同义词映射。

## 前置条件（硬门禁）

本技能是需求访谈的下游步骤，不是它的替代或并行选项。开始写 spec 前，必须同时满足：

- 访谈已经收敛：阻碍 spec 的关键问题已有结论，或用户明确同意将其作为假设/延期处理。
- 需求已经对齐：范围、主要流程、权限与可见性、非目标、验收标准已由用户确认。
- 有可追溯的输入：访谈/对齐流程的共识摘要、用户最新的明确确认、现有 spec 中已批准的内容，或已确认的父 spec 及其需求子集（创建子 spec 时）。

任一条件不满足时，不要开始起草 spec。先列出缺口，回到访谈/对齐流程补齐（如 `interview` 技能或等价流程），或直接向用户确认。用户说「整理 spec」本身不等于需求已经对齐。

## 开始前

1. 阅读项目的 agent 约定文件（如 `AGENTS.md` / `CLAUDE.md`），以及相关的正式 spec 与 issue。
2. 收集输入：
   - 用户的明确指令；
   - 访谈/对齐流程的结论或记录（如 `interview` 技能）；
   - 已确认的共识摘要；
   - 父 spec（若本次创建子 spec）；
   - 现有 spec（若本次是更新）。
3. 先建立四类清单：
   - 已确认事实与决策；
   - 假设；
   - 开放问题；
   - 明确不做或延期。
4. 按前置条件逐项检查；若关键信息缺失、矛盾或只有假设：
   - 不要进入起草；先回到访谈/对齐流程（如 `interview` 技能）补齐，或直接向用户确认；
   - 不得用默认值、行业惯例或自己的推断替代用户决策；
   - 「关键信息」至少包括：目标与成功标准、范围边界与非目标、主要流程、角色/权限/可见性、验收标准。
5. 确定正式 spec 的发布位置：本项目直接创建为 GitHub issue。

## 编写规则

- 只写长期有效的结论、范围、决策和规范；不要写访谈过程、文档清理/迁移记录、临时讨论或工作日志。
- 使用项目约定的文档语言（无约定时跟随用户语言）；代码标识符、命令、文件路径、协议/API 名称和专有名词可保留英文。
- 每条功能需求使用稳定 ID（如 `AGENT-01`、`CHAT-02`）；每个验收标准使用 `AC-...` ID。
- 范围必须同时写「包含」和「不包含」；边界要可判断。
- 假设必须显式标注，并写明影响与确认时机。
- 验收标准必须可观察、可测试，覆盖正常路径、失败路径、权限和隔离。
- 明确测试 seam：优先复用已有 seam，选择尽可能高、尽可能少的公共边界；新增 seam 要说明理由，并与用户确认。
- 术语与项目的 `CONTEXT.md` 或术语表保持一致；新增或修订术语时按 `project-memory` 规则处理。
- 不要把 nice-to-have 写成 must-have；不确定的内容放入开放问题。
- 不要复制大段已有内容；使用 issue 链接引用。
- 更新已有 spec 时保留已批准内容，明确列出本次变更；不要静默改写历史决策。
- 按项目约定维护 spec 状态；新建 spec 标为「草案（待评审）」，用户明确确认后才能改为「已确认」。状态流转见下。

## Spec 状态

默认状态流转（项目有不同约定时，以项目约定为准）：

| 状态 | issue 状态/标签 | 含义 |
| --- | --- | --- |
| 草案（待评审） | 开放 + `needs-info` | 尚未得到用户确认；不得拆票或作为验收依据 |
| 已确认 | 开放 + 无就绪标签 | 已得到用户确认；可拆票、可进入实现 |
| 已完成 | 已关闭 + 无就绪标签 | 不再维护，且相关任务均已完成 |
| 已取代 / 已放弃 | 已关闭 + `wontfix` | 被新 spec 取代或不再实施 |

- 已确认的 spec 不挂就绪标签。
- 拆票后保留 spec 为开放状态，标签不变；不要因为拆出 ticket 就加进度标签或关闭 spec。
- 主 spec 与子 spec 使用同一张状态表，不额外区分「主 spec 执行中」「子 spec 执行中」。
- 子 spec 关闭不自动关闭主 spec。
- 所有任务完成但 spec 仍需维护时，保持开放；不再维护时才关闭为「已完成」。
- 拆票或任务完成都不自动关闭 spec；关闭时不得残留就绪标签。

## 推荐结构

使用 `references/spec-template.md`。元数据至少包含：状态、日期、父 spec（子 spec 必填）、子 spec 列表、关联文档、关联 ticket。正文至少覆盖：

1. 摘要与定位
2. 目标与成功标准
3. 用户与角色
4. 领域模型与术语
5. 范围（包含 / 不包含 / 关键假设）
6. 功能需求（带 ID）
7. 非功能需求
8. 验收标准（带 ID，可测试；写明测试 seam）
9. 分期与里程碑
10. 风险与待定设计项
11. 参考文档

## 流程

1. 执行前置门禁检查；未通过则回到访谈/对齐流程，不进入后续步骤。
2. 读取输入，建立已确认/假设/开放问题/非目标清单。
3. 与现有 spec/issue 做一致性检查，找出重复、冲突和缺口。
4. 确定 spec 标题、发布位置、状态、父 spec/子 spec、关联文档和关联任务。
5. 按模板起草；需求 ID 和验收 ID 建立映射；明确测试 seam。
6. 逐项执行质量检查（见下）。
7. 在 GitHub Issues 中创建或更新 spec issue。
8. 输出变更摘要、覆盖范围和待确认项，请用户评审。
9. 用户确认后更新 issue 标签（移除 `needs-info`，已确认的 spec 不挂就绪标签）；任务拆分/拆票是独立的下游步骤，由 `to-tickets` 技能先展示简短概览并确认后执行，除非用户明确要求，否则不要在本技能中直接创建任务。拆票后保持 spec 为开放状态、就绪标签不变，不要因存在 ticket 就关闭 spec。

## 质量检查

- [ ] 已通过前置门禁：访谈收敛、需求对齐、输入可追溯。
- [ ] 目标、范围、非目标、成功标准齐全。
- [ ] 领域模型清楚，实体归属和数据隔离明确。
- [ ] 每条功能需求有 ID；关键验收标准能映射回需求。
- [ ] 测试 seam 已明确：优先复用已有 seam，选择尽可能高、尽可能少的公共边界。
- [ ] 术语与项目术语表 / `CONTEXT.md` 一致；新增术语已按 `project-memory` 处理。
- [ ] 正常路径、失败路径、权限/可见性、生命周期、持久化都有覆盖。
- [ ] 没有未标注的假设；没有过程性内容；没有未经验证的能力承诺。
- [ ] 文档语言、标题命名与链接符合项目规范。
- [ ] 若为子 spec：已声明父 spec，未扩大父 spec 范围，需求/验收 ID 可映射到父 spec。
- [ ] 与项目的 agent 约定、现有 spec 不冲突；冲突已列出并请求用户裁决。
- [ ] 新建 spec 保持「草案（待评审）」；更新已确认 spec 时保持其既有状态，不擅自降级或标为已完成。

## 与其他技能的关系

技能链路见项目的 agent 约定文件（如 `AGENTS.md`）。项目没有对应技能时，按项目实际流程执行。

- `interview`：负责提问和消除信息差，产出双方确认的共识摘要；本技能不重复访谈，也不跳过它。
- `decision-map`：大型未知探索先画决策地图，路线清晰后进入本技能；普通需求不需要地图。
- `to-spec`：只接收已对齐的需求，把共识固化为正式 spec；一次产出一份 spec，不在这里拆分任务。
- 子 spec：以已确认的主 spec 为输入，细化当前阶段或模块；不得扩大主 spec 范围。
- `to-tickets`：以已确认的子 spec 为来源，先向用户展示简短概览并确认，再拆分为任务、issue 或 ticket；拆票不改变 spec 的就绪标签。
- `tdd`：测试 seam 在本技能中确定，红绿循环由它执行。
- `implement`：按单张已确认 ticket 实现，不扩大范围。
- `implement-spec`：按 ticket 任务图执行整份已确认 spec，最终统一进行代码审查。
- `code-review`：以 spec 的需求轴审查实现，并输出独立的双轴报告。
- `pr`：生成结构化 PR 描述，汇总证据与合并风险。

## 复用

本技能依赖 `references/spec-template.md`；复制到其他项目时保留目录结构（至少 `SKILL.md` + `references/`）。

## 反模式

- 需求尚未对齐就直接开 spec，或用「先写一份 spec 看看」代替访谈。
- 把「用户要求整理 spec」误当作需求已确认，跳过前置门禁。
- 把访谈原文、聊天记录或「已清理/已迁移」之类的过程信息写入 spec。
- 用模糊词代替可验收标准。
- 把假设写成事实，或把开放问题藏在正文里。
- 只写验收标准却不写测试 seam，把测试位置留到实现阶段临时决定。
- 一次性把所有细节都写成 must-have，导致范围失控。
- 未经用户确认就把 spec 标为已确认，或提前拆分任务。
- 创建超过一层的 spec 嵌套。
- 子 spec 自行新增范围，或修改父 spec 已确认的验收标准。
- 预先创建所有阶段的子 spec，把未验证的设计提前冻结。
- 把「已拆票」等同于「spec 已完成」，或因 ticket 完成就自动关闭 spec。
- 把某个项目的专有路径、角色或 issue 结构硬编码进 spec 流程。
