# 测试驱动开发

## 调用方式

用户可显式触发，也可由 `implement` / `implement-spec` 在实现阶段调用。循环结束即返回；不负责提交、评审或发布。

## 目标

用红 → 绿循环产出值得保留的测试：只测公共行为，能在重构后存活，期望值来自独立来源。

## 前置条件（硬门禁）

- 测试 seam 已确认：写在 ticket 或 spec 中，或由用户当场确认。未确认 seam 不写测试。
- 要实现的行为已明确：来自 ticket 的交付行为，或 spec 的需求 ID / 验收 ID。
- 不在探索阶段：需要先验证方案可行性时用 `prototype`，不要在主线代码里试。

## Seam

seam 是测试所在的公共边界：从那里观察行为，不伸手进内部。

- 只测已确认的 seam；写测试前先说清这次测哪些 seam。
- 优先复用已有 seam，选尽可能高、尽可能少的公共边界，理想数量是一个。
- 每个 seam 用一句话说明它覆盖什么、漏掉什么。
- 新增 seam 需要理由，并请用户确认。

## 循环

一个循环只做一件事：

1. **红**：写一个失败测试，确认它因为预期原因失败，不是编译错误或环境问题。
2. **绿**：只写让这个测试通过的最小实现，不预判后续测试，不添加用不上的能力。
3. **下一个**：回到第 1 步，处理下一个 seam 或下一条行为。

- 先红后绿，不预先写一批测试。
- 一次一个 seam、一个测试、一份最小实现。
- 重构不在循环内。循环结束后按 `code-review` 的结论处理；发现与当前 ticket 无关的必要重构时，先说明并征求用户意见。

## 好测试与坏测试

好测试读起来像规格说明：描述「有什么能力」，不描述「怎么实现」。

- 只经过公共接口：不 mock 内部协作者、不测私有方法、不通过旁路（直接查库）验证。
- 一个测试一个逻辑断言。
- 期望值来自独立来源：已知字面量、worked example、spec。不按被测代码的算法重算期望值。
- 重构内部结构后测试仍应通过；没改行为却要改测试，说明测试写错了。

示例见 `references/tests.md`。

## mock 边界

只在系统边界上 mock：外部 API、数据库（优先用测试库）、时间与随机数、文件系统。

不 mock 自己控制的类、模块和内部协作者。为可 mock 性设计接口：依赖注入；外部操作按 SDK 风格拆成独立函数，而不是一个通用的 fetch 包装。

示例见 `references/mocking.md`。

## 完成判据

- 每条目标行为都有一个在已确认 seam 上的测试，且先红后绿。
- 相关测试与类型检查通过。
- 没有测试私有实现、内部协作者，或重算期望值。
- 没有为后续 ticket 提前写的测试或实现。

## 反模式

- 先写一大批测试再写实现（横向切片）。
- 在未确认的 seam 上写测试。
- 测试私有方法、mock 内部协作者、断言调用次数或顺序。
- 期望值由被测逻辑算出，测试构造性通过。
- 通过直接查数据库或读内部状态来验证行为。
- 把重构混进红绿循环。
- 为还没到来的需求提前实现能力。

## 与其他技能的关系

- `to-spec` / `to-tickets`：提供测试 seam、需求 ID 和验收 ID；seam 在那里确认，不在本技能临时决定。
- `implement`：单票实现时调用本技能完成红绿循环。
- `implement-spec`：整份 spec 执行时，每张票同样按本技能推进。
- `code-review`：评审结论驱动的重构在循环之外处理。

## 复用

本技能依赖 `references/tests.md` 和 `references/mocking.md`；复制到其他项目时保留目录结构（至少 `SKILL.md` + `references/`）。
