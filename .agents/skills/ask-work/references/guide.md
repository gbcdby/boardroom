# 工作技能使用指南

这套技能用于从想法、反馈或改进推进到约定的交付终点，也可以单独用于调查、设计、验证或理解项目。它适配不同项目和语言；具体工具、权限和交付规则以当前项目为准。

## 从一个目标开始

直接说明想解决什么、怎样算完成，以及希望做到哪一步。例如：

> 这个页面重连后会显示重复消息。先复现并修复，完成验证和审查后开 PR；本次先做到可审查。

`deliver-work` 会按实际缺口选择必要能力。只想调查、讨论或形成计划时，把这个终点说清楚；不需要按顺序手动调用所有技能。

不确定怎样开始，可以主动选择 `ask-work`：

> 我有一个方向，但还不知道值不值得做。推荐一个合适入口，给我一条开始用的提示。

## 第一次接入一个项目

**安装技能**让宿主发现这些入口；**项目接入**让它们复用该项目的约定。使用目标平台正式支持的方式安装已审查版本。仓库分发目录是 `.agents/skills/`；不要用安装过程覆盖已有同名技能或未经核对的项目规则。

需要整理项目适配时，主动选择 `setup-work`：

> 将已安装的工作技能接入这个项目，先识别已有规则、验证入口和交付方式，只补必要缺口。

已有清楚约定的项目可以直接开始工作。setup 不是每日前置步骤，也不会替你安装任意第三方技能、创建凭据或扩大权限。换项目时不沿用另一个项目的标签、目录、工具链或批准规则。

## 怎样显式调用

| 环境 | 常见方式 |
| --- | --- |
| ChatGPT | 在支持技能选择的界面输入 `@` 并选择技能 |
| Codex CLI / IDE | 使用 `/skills` 选择，或在提示中写 `$skill-name` |
| Claude Code / Cursor | 从技能菜单选择 `/skill-name`；插件名称可能带前缀 |

以实际菜单、安装版本和宿主文档为准。文件存在或调用配置正确，不等于已经在该宿主实测；本套件不会仅凭元数据声称跨宿主限制已生效。

## 四个由你主动选择的入口

| 你想做的事 | 入口 | 示例 |
| --- | --- | --- |
| 深入推敲目标、假设和方案 | `challenge-work` | “先挑战这个方案，抓最影响结果的几个问题，暂不实现。” |
| 落实裁决、改向、范围或停点 | `steer-work` | “接受方案 B，只适用于本地模式；做到演示版本后暂停。” |
| 整理或修订项目适配 | `setup-work` | “核对迁移后的工具链和项目约定，只更新发生变化的部分。” |
| 问用法、选入口、排查使用问题 | `ask-work` | “我想亲自验收这个版本，应怎样开始？” |

这四项配置为人工主动入口，调度器不自行启动。它们可使用允许组合的专业方法，但不能借读文件或子代理绕过入口限制。

普通语言仍能表达有效指令。直接说“暂停任务 A，任务 B 继续”“先让我看方案”“按 B 继续”，不需要先记住技能名。技能帮助完整落实复杂介入；实际暂停、取消和远端操作依赖宿主工具。

## 按情境使用现有能力

| 情境 | 可以使用的能力 |
| --- | --- |
| 希望持续推进到约定终点 | `deliver-work` |
| 需求模糊、问题未定位、资料与实现冲突 | `frame-work` |
| 行为、模块职责、接口或演进方案需要设计 | `design-work` |
| 并发、重试、状态机或协议值得形式化检查 | 独立的 `tla-verify-design` |
| 契约明确，需要落实变更 | `implement-work` |
| 需要执行检查，或独立判断变更 | `verify-work` 执行验证；`review-work` 按需求和项目标准审查 |
| 需要处理 PR、合并，或实际发布 | `land-work` 负责 PR 与合并；`release-work` 负责发布和目标环境验收 |
| 想看懂进度、行为、架构或决定依据 | 只读的 `brief-project` |
| 在已授权的多 Agent 房间工作 | `work-in-room` |
| 反复返工、误报、漏检或协作不收敛 | `improve-workflow` |

这些是可选择的能力，不是固定流水线。形式化模型结果、源码核对和实际运行证据分别记录；一个层次通过不替其他层次作保证。没有 GitHub、boardroom 或某项可选技能时，使用当前可用方式完成不受影响的部分；缺少目标所需能力时说明具体差距。

## 让汇报符合你的阅读需要

可以随时要求：

- “给我短版，只讲成果、架构变化和真正需要我决定的事。”
- “上一条没跟上，先用一个具体例子讲清楚。”
- “解释为什么选这个方案，把替代项和被排除的意见也给我看。”
- “只看这个子系统，从行为讲到状态归属，暂不改代码。”

`brief-project` 可以按这些问题展开。阅读简报不代表接受方案，也不会自动修改任务或批准发布。

## 看清实际到达哪一步

- 有设计或模型：已有相应产物，不代表业务实现完成。
- 验证通过：针对报告列出的对象、环境和范围；后续变化可能需要重新检查。
- PR ready：达到项目约定的 ready 条件，仍需核对平台检查和实际合并状态。
- 已合并：目标分支已包含变更，不代表已发布或部署。
- 已发布 / 已部署：需要目标位置的实际证据；用户验收按约定场景另行确认。

“我接受这个架构”“允许合并这个 PR”“产品体验满意”是不同决定。有效授权继续适用；用户只说看过或没有回复，不增加新的授权。人工认可也不会把失败检查改写为通过。

## 常见问题

**必须先 setup 吗？** 不需要。Agent 可以复用现有约定并按任务发现工具。缺少必要能力时，应指出具体缺口。

**能只做设计或调查吗？** 可以，明确终点即可。TLA 技能负责设计和形式化验证，后续实现由其他能力承担。

**每阶段都需要我确认吗？** 不需要。已有授权能推进时继续；你可以主动指定“设计后先给我看”“发布前停一下”等局部停点。

**暂停消息发出就算停了吗？** 不算。需要区分已请求、已收到、实际停止以及无法确认；已发生的外部效果不会因发出暂停而自动撤销。

**安装后找不到入口怎么办？** 核对实际安装路径、技能名、启用状态、宿主支持和重名项。配置或文档核对通过，只能说明对应检查完成；真实发现与调用仍需在目标环境验证。

**给别人使用时要带哪些内容？** 提供对方有权访问的完整技能目录及本指南，保留附带资源和来源。让对方按自己的项目规则接入；不要夹带凭据、个人任务记录或本项目的授权。
