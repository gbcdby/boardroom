# 自主推进交付

围绕明确的用户结果推进；在已有授权内执行可调查、可实验、可验证的工作。把需要人判断的事项整理成具体选择，并继续无关的已授权工作。

## 开始时

1. 读取项目约定、当前工作记录和实际工具能力。保留用户的最近要求、既有授权和已确认决定。
2. 确定 delivery_target：investigated、designed、verified、pr_ready、merged、published、deployed 或 accepted。用户只要求计划时，计划本身就是终点；用户已要求实施时，计划之后继续。
3. 固定当前处理对象：设计版本、完整工作树快照、提交及基线、集成候选、产物或环境。分支名和聊天摘要不足以标识实际内容。
4. 优先复用已有 issue、tracker、工作记录和专业产物。需要新记录时使用 [工作契约](references/work-contract.md)；小任务使用等价紧凑文本。
5. 检查项目已有能力适配。boardroom 试验场读取 [boardroom 项目适配](references/boardroom-project.md)，其他项目不加载它。

## 选择必要能力

| 当前缺口 | 使用的方法或已安装能力 |
|---|---|
| 不清楚问题、事实、目标和范围 | frame-work |
| 行为、模块边界或取舍不明确 | design-work |
| 并发、重试、恢复或协议存在值得建模的风险 | 独立 tla-verify-design |
| 已有可执行契约，需要实现 | implement-work |
| 需要真实候选的运行证据 | verify-work |
| 需要独立判断实现和契约 | review-work |
| 需要 PR、反馈处理与授权集成 | land-work |
| 目标包含发布、部署或交付位置验收 | release-work |
| 人需要掌握架构、行为和变化 | brief-project |
| 当前工作在已授权协作房间中 | work-in-room |
| 发生漏检、误报、重复返工或能力版本变化 | improve-workflow |

这些是可替换能力，不是强依赖或固定顺序。缺少某个 Skill 时使用其专业方法并说明实际执行者；不要声称调用了不存在的能力。使用第三方 Skill 前核对其调用限制、适用版本和前置条件；禁止通过直接读盘执行来绕过禁止模型调用的限制。

## 拆解和推进

- 把结果拆成能独立核验的工作单元，记录依赖、负责人、写入范围、必要证据和预算。按用户价值或可观察行为切分，不强制每个任务都有 UI。
- 优先完成一个实际贯通的最小切片，再扩大并行度。迁移可把可撤销准备与难以撤销动作分开，但可撤销不自动意味着已获授权。
- 仅在依赖和写入范围允许时并行。单一工作区或独占产物同时只有一个明确写入 owner；隔离工作区的变更在集成候选上验证。
- 无需所有讨论经过一个中央 Agent。参与者可以在范围内提议、求助和移交；权威状态和实际操作由现有工具保存或约束。
- 房间不提供原子领取、租约或 fencing 时，不虚构这些保证。采用明确的单协调者分配和隔离工作区，标明它是工作约定。
- 不按模型品牌固定岗位。先满足工具、环境、权限、独立性与预算条件，再参考该 harness × 模型 × 工具 × Skill 组合的实际表现。
- 不把日常过程全部推给用户。默认汇报结果变化、关键证据、阻塞与必要决定；原始资料按需展开。

## 处理结果与失效

1. 收到阶段结果后核对 subject、证据范围和未解决项；COMPLETE 只表示当前职责完成。
2. 候选、相关基线、契约、配置或环境变化时重新评估相关证据。记录可复用部分的理由；不把旧通过直接用于新对象，也不无差别重跑无关检查。
3. TLC 的有限模型通过、源码对应核验、实际运行验证分别记录。独立 TLA Skill 完成后接回整体工作，但不要求它实现业务或编写项目测试。
4. 发现问题按原因返回：事实/范围回 frame；语义回 design；模型问题回 TLA；实现问题回 implement；工具环境故障先处理环境。
5. 给审查和讨论设定有界的轮次、费用或无进展阈值。达到阈值时转调查或重设计，不能把预算耗尽当通过。
6. 保留反例和有效异议。多数票或另一模型的同意不能代替可核查证据。
7. 使用实际 API/CI/仓库事实判断是否达到目标。PR 创建、auto-merge 已启用、排队、工具返回 completed 均不等于已合并或已交付。

## 恢复、暂停和取消

恢复时重新读取权威状态、外部操作结果与当前所有权，再决定下一步；不直接重放上次会话最后一条命令。超时后先核对是否已产生副作用，再决定能否重试。

用户暂停时保存当前对象、未提交内容、已完成/未完成操作和恢复条件。取消请求、已观察取消、执行停止与外部效果分别记录；不承诺停止信号能撤销已经完成的操作。

缺少最终授权时先完成已授权的调查、实现、检查和具体可审查方案，再提交决策。有效授权继续适用；用户沉默、阅读摘要或房间角色声明不创造授权。

## 交付回执

按 [结果模板](assets/work-result.template.json) 返回 work-result/v1：work_id、skill、outcome、subject、evidence、unresolved、changed_assumptions、next_action。同时说明目标终点与实际到达位置。

outcome 使用 COMPLETE、PASS、FAIL、INCONCLUSIVE、BLOCKED、NOT_RUN；保留原工具状态作为证据。只有达到约定终点才把整体工作标为 delivered。

可用 Python 3.10+ 运行 scripts/validate_result.py 检查 JSON 结构和直接证据引用一致性。它只检查记录，不验证证据真实性、不授予权限、不执行调度或合并。

方法来源与适配边界见 [来源](references/sources.md)。

JSON 交接时，next_action 与 evidence.scope 使用非空文本，结构化详情另放扩展字段；subject.id 使用含真实版本的不可变身份。引用不同对象的原始材料时保留原 subject_id 并标 relation=background，直接结论绑定当前对象；独立工具的原报告原样保留，由交接层包装，不要求它改用本格式。
