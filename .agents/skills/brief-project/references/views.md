# 简报视图规则

## 资料新旧与权威来源

按问题选择原始证据，而非给所有来源设一个固定高低顺序：运行版本看目标环境；合并状态看代码托管平台；接受的设计看正式决定；模型检查看对应模型与配置的运行产物。

源码静态核对可以证明某路径存在，不足以证明该环境实际运行成功。文档与代码不符时显示差异及版本，不能悄悄改成更乐观的状态。

重要主张保留证据引用。另一个 Agent 的完成描述只是一项陈述，直到有足够原始证据支撑；多份摘要重复该陈述不增加可信度。

## 架构变化的两条比较线

1. **相对上次观察**：帮助用户发现最近发生的变化。
2. **相对已接受基线**：帮助用户看到多次小改动累积后的设计偏移。

两个标识分别保存。找不到基线时写“尚无可确认的接受基线”，不能写“无架构偏移”。模块边界、状态归属、依赖方向、公开接口和部署边界是有用的比较对象。

## 证据有效性

检查证据指向的候选、基线、契约、环境及规则版本。相关变化后，标明待重评；若项目已有可追溯的影响分析支持局部复用，展示该依据。不得仅因时间较新或结果为 PASS 就认为覆盖当前对象。

把以下内容分别呈现：已检查、未检查、检查失败、因环境受阻、证据已过期。不能把“没有报告问题”写成“没有问题”。

## 决策卡

每张卡只包含一个可独立决定的问题：

- 要决定什么，哪条已接受承诺会变化；
- 为什么现有事实和授权不能直接决定；
- 推荐项、替代项与各自后果；
- 支持它们的证据和主要未知；
- 影响哪些工作，等待有何后果；
- 适用范围、前提和已有决定引用。

同名问题不一定是同一决定。跨项目授权、不同数据后果、前提变化与不同不可逆边界不能被摘要合并。

## 只读视图的停止条件

完成用户请求的理解范围即停止。缺少新的模型、运行验证或权限时，显示缺口并返回。不要领取任务、启动服务、运行 TLC、确认房间消息或更新“已接受”字段来让简报显得完整。
