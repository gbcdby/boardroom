# 项目近况

用读起来像同事汇报的白话，让人快速看懂做成了什么、设计哪里变了、卡在哪里、是否需要自己决定。以当前权威记录为依据，不把摘要变成另一套项目事实。

## 只读边界

- 允许读取项目记录、源码、已有模型和图、运行证据、PR 与目标环境的只读状态。
- 不领取任务、不确认消息、不修改授权、不接受架构基线、不执行合并、部署、模型检查或应用验证。
- 可以输出用户请求的简报文件或阅读视图；不得因此回写工作状态、把任务标为完成或把“已看过”标为“已接受”。
- 若需要新的运行证据或更新模型，列出精确缺口并交回相应工作。不要为制作简报调用带执行副作用的生成流程。
- 不依赖 boardroom 或特定宿主。房间只有带副作用的加入接口可用于取数时，使用已有可读资料并说明缺口，不擅自入群。

## 表达与篇幅

- 开头一句直接回答用户最关心的问题，说明结果或实际影响；不先介绍工作方法，不回放执行过程。
- 日常近况以约 200–400 汉字的一屏概览为目标；单一问题可以只有一两句。用户要求深入时再展开相关部分，追问只补缺少的信息。篇幅是软目标，重要阻塞、未知、分歧和待决事项不能因此消失。
- 用短句、具体主语和动作，减少专业词汇、缩写和项目黑话。必须保留的术语第一次出现时用短语解释；技术标识、完整版本和字段放在依据或按需展开的细节中。翻译术语时保留适用范围，不把“没验证”说成“没问题”。
- 设计变化要解释“谁负责什么、哪里变了、会有什么影响”，保留关键取舍；不能为了简短只剩任务数量、状态词或空泛的“架构已优化”。
- 有多项状态、方案或改动前后的关系可比较时，默认用短表；需要解释依赖、分支和信息流时优先用小图；有真实数据的趋势才用数据图。单个事实或图表不增加清晰度的短答直接写。日常简报通常选择一张最有用的图或表，不为凑图强画流程。
- 图标仅辅助扫读，配合“已合并”“还没检查”等明确文字；不用颜色或单个绿灯代表全部完成，不给每句话加装饰。图表讲过的内容不再逐项复述，必要时补一句影响。
- 关键结论旁放简短、可打开的依据链接。保留观察时间、对象版本和来源范围；当时效、版本差异或证据不足影响判断时，在正文直接说明。用户未要求定位代码时，提交哈希和内部短号留在依据中，缩短后也不必放进正文；有定位价值的任务或 PR 编号可用短链接呈现。
- 省略空栏目、重复结论和泛泛的收尾；没有待人决定的事项就不制造问题或确认环节，用户问到时直接说清。

## 1. 确定用户想掌握的范围

1. 明确是一个工作项、一个子系统、整个项目，还是明确指定的一组项目。不要为了“全面”读取无关项目。
2. 识别用户此刻的问题：发生了什么、现在怎样工作、为何改变、还缺什么，或哪里需要决定。
3. 找到项目既有的权威工作单、架构基线、代码和证据记录。不存在的记录直接标明，不从最近聊天补造批准或部署事实。
4. 记录本次观察时间、所读对象的版本和资料时效；把旧报告与新事实分开。
5. 必要时做有界只读核对。摘要与原始材料矛盾时优先查明来源，不通过多数摘要投票解决。

按用户此刻需要选择深度：快速回看只讲关键变化；理解子系统时用具体例子解释行为、结构和设计理由；上一条没讲清时只补缺失上下文，不重做整份项目调查。事实、推断和未知分别表达，按追问展开。

用户要求重述目标时，区分明确要求与当前理解；复述不意味着已获确认，也不自动增加等待确认的停点。问“为什么”时查实际依据，找不到历史理由就说明未知，不补造决策动机。

## 2. 按实际目标报告状态

分别表达目标终点与当前事实，避免一个笼统的“完成百分比”。

| 已观察事实 | 不可推导的结论 |
| --- | --- |
| 设计或模型产物存在 | 代码已实现或已验证 |
| 某个候选检查通过 | 修改后的候选仍通过 |
| PR ready 或自动合并已设置 | PR 实际进入了目标分支 |
| 代码已合并 | 已发布、已部署或已经验收 |
| 部署请求已受理 | 目标环境确实运行指定版本 |
| 一次验收通过 | 无限期无故障 |

为关键结论提供可以打开或读取的证据。证据本身缺少对象、环境或范围时，显示为受限或未知，不自行补齐。

## 3. 按问题选择阅读视图

以下视图按需选用，不要求每次全部展开。问进度时优先成果、当前卡点和需要人的事；问设计时解释相关结构和取舍；重大设计变化即使在进度简报中也保留一句实际影响。

### 行为视图

说明用户或调用者在关键情境下会经历什么，突出本次修改的路径、异常和尚未明确的语义。读取已有有效图；无图时可从已核对事实制作带版本与限制的阅读图，不借此创造新的产品承诺。

### 架构视图

展示相关模块职责、数据与状态归属、关键接口和依赖。区分拟议、已实现、已合并、已部署和已验证状态，不把计划节点画成已经运行的系统。

架构类简报同时检查相对上次观察的变化，以及相对已接受基线的累计变化；展示与问题有关的差异，不固定输出两套清单。若基线不存在或过期，用白话说明无法判断整体改了多少；不要自动把当前架构变成新基线。

### 变更与证据视图

说明本次实际成果、影响范围、通过或失败的检查、未覆盖部分以及证据失效原因。模型结果、源码对应与真实运行结果分开展示，不用一个绿灯代表全部层次。

## 4. 把人的注意力放到决定上

- 默认优先展示实际成果、重要架构或行为变化、交付阻塞和确需人的决定。
- 每个决定默认用“要你决定什么、建议及主要代价、影响与等待后果”组织短文字；已有事实、替代项和适用前提只在影响判断时展开，依据紧邻结论。保留能够改变选择的信息，不机械填写长卡。
- 将同一前提和权限范围内的重复决定合并；前提变化、作用范围不同或后果不同的决定保留区别。
- 已有有效决定直接引用。人的沉默不新增授权，阅读简报不接受新基线。
- 保留影响当前交付的未解决分歧，说明证据差异；不要通过压缩摘要抹去少数但有依据的反例。
- 资料很多时先给短摘要和展开入口；重要阻塞与实质待决事项全部保留可见索引，不因显示数量或字数限制而静默消失。对仍可由 Agent 处理的问题说明当前卡点，不顺手改成等待用户拍板。

## 5. 需要时增加房间视角

只使用当前房间真正提供的读取能力，展示与用户问题有关的任务、角色、协作事件和证据。

- 区分全局身份、项目成员、连接状态、工作状态和任务完成状态。
- 不把成员在线、正在等待或聊天活跃解释为工作已经推进。
- 展示反复交接、无新增证据的讨论和影响交付的等待；没有测量依据时不根据消息数量评价贡献。
- 跨任务共享决定按适用范围去重；原始讨论保留可追溯入口，不要求用户逐个阅读每位 Agent 的日志。

## 6. 输出并结束

使用 [简报模板](assets/brief.template.md) 的必要部分。默认一句话结论，加最有用的小表、小图或少量短句；只在有内容时增加“卡在哪里”或“需要你决定”。结论、图表与依据避免重复；不要回放完整执行时间线。

完成用户所问的理解范围即结束；未检查和不确定的部分直说。用户没有要求时，不附机器记录、字段清单或长篇技术附录。

## 7. 仅在接收方需要时生成机器交接

面向人的简报与机器记录分别组织。只有实际接收方要求结构化结果时，才用 `schema_version: work-result/v1` 交接：`work_id`、`skill`、`outcome`、`subject`、`evidence`、`unresolved`、`changed_assumptions`、`next_action`。`subject` 至少有 `kind` 和实际 `id`；聚合视图列出被汇总的真实对象。证据记录出处、范围、状态、提供者和对象版本；不要把这些字段自动贴进人类简报。

- **COMPLETE**：请求范围内的阅读视图已形成；仍可包含明确标注的未知或失败。
- **INCONCLUSIVE**：关键事实相互冲突，现有只读依据不能支持用户要的结论。
- **BLOCKED**：缺少必要读取权限或关键资料，提供已能确认的部分和具体缺口。

将 `next_action` 作为建议返回，不执行它。简报产出完成不代表项目目标完成，也不构成新的批准。

静态源码事实使用 `status: OBSERVED` 与 `kind: source_inspection`；引用旧实测使用 `HISTORICAL` 并保留其对象与日期。证据可记录 `id`、`locator`、`scope`、`status`、`producer`、`subject_id`，不把静态或历史证据标为当前实测 `PASS`。

JSON 交接时，next_action 与 evidence.scope 使用非空文本，结构化详情另放扩展字段；subject.id 使用含真实版本的不可变身份。引用不同对象的原始材料时保留原 subject_id 并标 relation=background，直接结论绑定当前对象；独立工具的原报告原样保留，由交接层包装，不要求它改用本格式。
