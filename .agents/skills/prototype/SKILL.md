# 一次性原型（Prototype）

## 目标

用最小、可运行、可丢弃的产物回答一个具体设计问题。结论进入决策记录；原型代码不进入主线，也不当作最终实现。

## 前置条件

- 问题明确：要验证什么、什么结果算回答。
- 有时间盒（例如一次会话或固定分钟数）；到点停止。
- 知道结论写到哪里：决策票、决策地图或项目约定的记录位置。
- 用户明确要求做原型。原型不是实现，不承接正式验收。

## 选择分支

先确定要回答哪类问题，问题决定产物形状：

1. **逻辑 / 状态**：状态机、reducer、算法或协议流程是否合理。
   - 产物：一个可运行的脚本、HTML 或 CLI，能驱动状态、覆盖难以在纸上推演的案例。
   - 每次操作后打印或渲染完整相关状态。
2. **UI**：应该长什么样。
   - 产物：同一路由下多个差异明显的变体，可切换；记录截图和切换方式。
   - 不做视觉打磨，重点是让选项具体到可以讨论。
3. **接口 / 可行性**：两个组件、宿主或协议能否接上。
   - 产物：最小端到端 harness、假依赖或适配器骨架，证明关键路径可行或不可行。
   - 记录真实命令、宿主版本和失败点。

如果问题确实模糊且用户不在，按周边代码选择最接近的分支，并在原型顶部写明假设。

## 规则

- 从第一天起就明确是一次性的；放在靠近目标模块的位置，但命名清楚，不进入生产路径。
- 一条命令就能跑，不要求用户先理解项目。
- 默认不持久化；需要数据时用临时文件或 scratch DB，并明确标注可清除。
- 跳过打磨：不加测试、不做过多的错误处理、不做抽象；只保证可运行、可观察。
- 展示状态：每次操作或变体切换后，输出相关状态，让用户看到变化。
- 记录结论：问题、尝试、证据、结论、仍未知的项。
- 不留主线：原型放在一次性分支或临时目录，从决策票链接；验证过的决策进入 spec 或实现，不把原型代码直接合并。
- 到时间盒结束就停，不因「快完成了」而延长。

## 输出模板

```markdown
## 问题

<这次原型要回答什么>

## 分支与假设

<逻辑 / UI / 接口可行性；关键假设>

## 运行方式

<一条命令、入口、需要的环境>

## 证据

<截图、日志、命令输出、宿主版本>

## 结论

<能 / 不能 / 仍需什么；区分已验证和推断>

## 未验证项

<没有就写「无」>

## 决策去向

<写回哪张决策票；哪些结论进入 spec 或实现>
```

## 反模式

- 把原型做成生产功能，或直接合并到主分支。
- 加测试、持久化、抽象和完整错误处理，导致时间盒失控。
- 没有明确问题就开始写代码。
- 超出时间盒继续打磨，把探索变成交付。
- 把「能跑」当成「设计已确认」。
- 原型结论只留在聊天里，没有写回决策票。

## 与其他技能的关系

- `decision-map`：解决其中的 prototype 票，结论写回票并更新地图。
- `research`：纯事实查证用它；需要跑代码或做交互才能回答时用本技能。
- `to-spec`：原型的结论作为设计输入；不要把原型代码当作最终实现。
- `implement` / `implement-spec`：验证后的实现按正常 ticket 流程重写，不继承原型的临时结构。
