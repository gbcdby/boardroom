# 项目需求访谈

## 调用方式

本技能由用户显式触发。完成后提示用户下一步（通常是 `to-spec`）；不要自动调用其他用户显式触发的技能。

## 目的

通过与用户的多轮问答，把阻碍 spec、任务拆分或技术选型的关键未知项变成有来源的已确认事实，最终产出双方认可的共识摘要。目标不是一次问完所有问题，也不是替用户做决定。

## 项目适配

本技能默认使用下列约定；宿主项目有不同规范时，以宿主项目为准：

| 用途 | 默认约定 | 说明 |
| --- | --- | --- |
| agent 约定 | `AGENTS.md`、`CLAUDE.md` 或等价文件 | 先读其中的流程与边界要求 |
| 项目约定 | `AGENTS.md` 或项目约定 | 决定 spec 的发布与状态更新方式 |
| 正式 spec | issue tracker | 访谈结论的下游产物 |
| 任务跟踪 | 项目约定位置（issue tracker 或项目管理工具） | 用于确认任务拆分方式 |
| 临时输出 | `.agent-output/` 或项目约定目录 | 存放访谈笔记与草稿 |

## 开始前

1. 阅读项目的 agent 约定文件（如 `AGENTS.md` / `CLAUDE.md`），以及正式 spec、issue 中与当前主题相关的内容。
2. 建立初始信息地图：
   - 已确认事实（注明来源）
   - 假设（尚未确认）
   - 已发现的矛盾
   - 未知项（按「影响 × 不确定性」排序）
3. 工作笔记写入项目的临时输出目录（默认 `.agent-output/project-interview/<topic>-<YYYY-MM-DD>.md`；按项目约定调整），作为临时过程文件。

已有文档明确回答的内容直接引用，不再询问。发现文档之间冲突时，先引用原文，再把裁决交给用户。

## 访谈模型：设计树与 frontier

把需要确定的事情组织成一棵**设计树**：每个决策会分出依赖它的后续决策。

- **frontier（前沿）**是当前所有前置条件已经确定的决策，也就是现在就能问、不需要猜测未答问题的问题集合。
- 每轮询问整个 frontier：问题编号，每个问题给出你的推荐答案和主要取舍。
- 某个问题的答案依赖同一轮里尚未回答的问题时，把它放到下一轮；不要在同一轮里预设答案。
- 事实由 agent 负责查找：仓库、文档、命令、宿主能力和公开资料都属于可自查范围。用户负责的是决策、偏好和取舍。
- 用户回答后重算 frontier，再问下一轮；直到 frontier 为空。

宿主提供选项式提问工具时（如 Claude Code 的 `AskUserQuestion`），优先用它承载决策类问题；单次调用有数量上限时，在同一轮内分多次提问，保持轮次语义不变。

## 每轮流程

1. 列出当前 frontier，并按「影响 × 不确定性」排序。
2. 对每个问题给出：问题、推荐答案、主要取舍；能收敛为选项时给出互斥选项。
3. 用户回答后：
   - 先复述理解，再记录；
   - 标注回答属于事实、偏好、假设还是非目标；
   - 更新「已确认 / 待确认 / 明确不做或延期」清单；
   - 指出新出现的矛盾、依赖和风险；
   - 重算 frontier，进入下一轮。
4. 每轮结束给出简短状态：新增确认、仍待确认、下一轮主题。

## 提问质量

- 先问「是什么、为谁、为何做、怎样算成功」，再问实现细节。
- 对关键回答追问落地语义：如何验证？失败时怎么办？谁负责？边界在哪里？
- 区分 must-have、nice-to-have、later；不把 nice-to-have 写成承诺。
- 用户说「不确定」时，给出 2–3 个合理选项与取舍，或标记为待验证假设；不替用户拍板。
- 每个问题都应能改变范围、架构、验收或成本；没有决策价值的问题直接删掉。
- 不把推断、默认值或行业惯例写成已确认事实。

## 收敛条件

以下条件同时满足时停止访谈：

1. frontier 为空：每个分支要么已有结论，要么被用户明确延期或放弃。
2. 已确认项之间没有未解决的矛盾。
3. 剩余未知项都是非阻塞细节，且已记录。
4. 用户认可下面的共识摘要。

## 结束输出

输出一份共识摘要，包含：

- 目标与成功标准
- 范围（做 / 不做）
- 关键决策及理由
- 关键领域模型与运行环境约束（例如接入、投递、唤醒、状态、权限；按项目领域调整）
- 未决项与负责人/触发条件
- 假设与风险
- 建议的下一步（spec、原型或任务拆分）

请用户确认摘要。确认后：

1. 若进入 spec 阶段，使用项目中的 spec 编写技能（如 `to-spec`）或等价流程，将摘要整理为项目的正式 spec；未确认摘要前不要开 spec；
2. 需要长期保留的决策按项目约定处理；
3. 清理或注明临时输出目录中的笔记，不把过程稿当作正式结论。

## 话题覆盖

使用 `references/topic-coverage.md` 作为通用遗漏检查清单；项目有更具体的话题清单时，以项目清单为准。不必逐条提问，也不要一次覆盖全部话题。

## 复用

本技能依赖 `references/topic-coverage.md`；复制到其他项目时保留目录结构（至少 `SKILL.md` + `references/`）。

## 反模式

- 问题太泛，用户只能回答「看情况」。
- 把能自己查到的事实抛给用户，或让用户代替 agent 做检索。
- 同一轮里询问依赖未决答案的问题，导致回答互相打架。
- 用户已明确的需求被重复询问。
- 用问卷轰炸用户，或长时间不问关键决策。
- 把未回答的问题按默认值写成设计。
- 在用户确认共识摘要前直接进入 spec 或任务拆分。
- 未达到收敛条件就输出「最终 spec」。
- 把某个项目的专有路径、角色或流程硬编码进访谈流程。
