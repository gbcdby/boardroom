# 会话交接

## 调用方式

本技能由用户显式触发。写完后只报告交接文档路径、建议技能和第一步动作；不要自动开始下一项工作，也不要把它当作继续执行的授权。

## 目的

把当前会话的工作状态压缩成一份给**全新会话**的交接文档，让下一个 agent 用尽量少的上下文恢复工作。它不是聊天记录摘要，也不是 spec、ticket 或项目记忆的替代品。

与上下文压缩的区别：`/compact` 用于在同一会话继续；handoff 用于换会话、换 agent、切分并行范围或重新聚焦一个目标。用户只是想在当前会话继续时，建议直接压缩，不生成交接文档。

## 项目适配

| 用途 | 默认约定 | 说明 |
| --- | --- | --- |
| 交接文档位置 | `.agent-output/` | 临时产物，不提交；不写 `docs/`、仓库根目录或源码目录 |
| 文件命名 | `<YYYY-MM-DD>-<slug>.md` | slug 使用 kebab-case |
| 正式 spec / ticket | GitHub Issues | 交接文档只引用 issue 编号或链接 |
| 产品架构基线 | `docs/architecture/` | 用路径和章节号引用 |
| 项目记忆 | `CONTEXT.md` | 跨会话长期有效的事实；交接文档是临时的 |
| 文档语言 | 中文 | 标识符、命令、路径和 API 名保留英文 |
| 敏感信息 | 不写入 | 密钥、令牌、密码、个人信息一律脱敏 |

## 前置条件

- 用户已说明下一次会话的用途或目标；没有说明时先问一句，不自行猜测。用途决定哪些内容值得写。
- 已确认交接对象：同一 agent 的新会话、另一个宿主（Claude Code / Codex CLI）或并行子任务。
- 已读取真实状态，而不是凭记忆：分支、工作区改动、提交、issue 状态、测试结果。
- 用户只是想继续当前会话时，提醒其使用上下文压缩；不要用交接文档替代。

## 流程

1. 明确下一次会话的目标和边界：要完成什么、不做什么、何时算完成。
2. 盘点真实状态：
   - `git status`、当前分支、最近提交、未提交/未跟踪文件；
   - 相关 issue 的编号、状态、依赖；
   - 最近一次验证的命令和结果；
   - 已确认但尚未写入正式产物的决定。
3. 区分内容归属：
   - 已在 spec、issue、文档、提交、PR 中的内容，只写指针；
   - 只存在于本次对话、但后续仍需要的决定，建议先写入 issue、`CONTEXT.md` 或架构文档；未写入时在交接文档中标注「仅存在于本次对话，需重新确认」；
   - 与下一次目标无关的历史直接省略。
4. 按下一次目标裁剪文档：优先写当前状态、阻塞、下一步和证据，不写完整过程。
5. 明确证据等级：
   - 已验证：写命令、结果和日期；
   - 未验证/推断：单独列出，不写成事实；
   - 已知失败或风险：写清现象和影响。
6. 脱敏：移除 API key、token、密码、个人身份信息和内部敏感数据。
7. 保存到 `.agent-output/<YYYY-MM-DD>-<slug>.md`；目录不存在时创建。
8. 自检后向用户报告：文件路径、下一次会话建议调用的技能、第一步动作。

## 交接文档模板

```markdown
# Handoff：<主题>

日期：<YYYY-MM-DD>
下一次会话目标：<一句话>
交接对象：<同一 agent 新会话 / 另一宿主 / 并行任务>
工作区：<分支、HEAD、是否有未提交改动>

## 当前状态

- 已完成：
- 进行中：
- 未开始：

## 关键产物（只给指针）

- 产品基线 / 架构：`<path>` §<章节>
- spec / ticket：<issue 链接或编号>
- 代码 / 提交 / PR：<SHA、分支、PR 链接>
- 验证记录：<命令与结果所在位置>

## 已确认的决定

- <决定>（来源：<issue/文档/提交>）

## 未决与阻塞

- <问题>；需要 <谁> 在 <何时> 确认。

## 下一次会话的下一步

1. <具体动作>
2. ...

## 建议技能

- `<skill>`：<为什么、在什么时候调用>

## 不要做

- <明确排除的范围、已否决的方案、不能触碰的文件或边界>

## 验证状态与风险

- 已验证：<命令、结果、日期>
- 未验证：<假设或待实测项>
- 已知风险：<...>

## 敏感信息

- 本文档不包含密钥、令牌、密码或个人信息。
```

## 质量检查

- [ ] 下一次会话的目标写在文档最前面，且足够具体。
- [ ] 文档中的状态与 `git status`、提交和 issue 实际状态一致。
- [ ] 没有复制 spec、ticket、diff 或大段代码，只使用指针。
- [ ] 已验证和未验证的内容分开；没有把推断写成事实。
- [ ] 下一步是具体动作，不是「继续推进」这类空话。
- [ ] 建议技能与下一次目标匹配，并说明调用时机。
- [ ] 已列出范围外事项、已否决方案和不能触碰的边界。
- [ ] 没有密钥、令牌、密码或个人信息。
- [ ] 文档保存在 `.agent-output/`，未被提交。
- [ ] 没有把交接文档当作需求确认或执行授权。

## 与其他技能的关系

- `to-spec` / `to-tickets`：负责产出正式 spec 和 ticket；交接文档只引用它们，不替代。
- `implement` / `implement-spec`：下一次会话可能调用的执行技能；交接文档应写明当前 ticket 和前置依赖。
- `code-review` / `pr`：交接时写清固定基准点、评审状态和 PR 链接。
- `project-memory`：维护跨会话长期有效的项目事实；交接文档是一次性的任务上下文，不能替代 `CONTEXT.md`。

## 反模式

- 把整段对话、完整 spec、ticket 正文或 diff 复制进交接文档。
- 不说明下一次会话的目标，输出一份泛化的聊天摘要。
- 把交接文档写进仓库、`docs/` 或提交到 git。
- 把未验证的宿主能力、测试结果或推断写成事实。
- 把交接文档当成用户批准，或未经确认就继续执行。
- 写入密钥、令牌、密码或个人信息。
- 只写「继续做」而没有具体下一步和阻塞。
- 用交接文档代替 issue、spec 或项目记忆来保存需要长期存在的信息。
