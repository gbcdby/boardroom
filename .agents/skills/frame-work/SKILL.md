# 调查需求与问题

把请求变成有事实依据、范围清楚、能够验收的工作。先解决可以调查的问题，再把确实需要人的取舍集中呈现。

## 输入与职责

- 读取用户的实际目标、已有工作单、项目规则、当前实现与可用证据；复用已知信息，不重新进行完整访谈。
- 确认本次终点是调查结论，还是外层交付任务的前置步骤。完成本 Skill 后交回调用者，不把定界完成当作整个交付完成。
- 允许在既有权限内读取资料、运行针对性的复现与隔离实验；不顺带修复业务代码、发布系统或改写已确认的产品承诺。
- 不依赖 boardroom、特定语言、某家模型或其他 Skill。使用房间时，读取实际接口和工作事实，不假定房间已经支持任务认领或持续唤醒。

## 1. 建立最小上下文

1. 找到项目的权威记录位置，先读取适用的工作约定和已有结论。详细工单、设计和运行证据可以分处不同系统，只保留引用。
2. 固定正在调查的对象：版本、工作树、配置、环境和时间。未提交或未跟踪内容影响结果时，单独记录，不能只写分支名。
3. 用一两句话复述用户想看到的变化，以及如何判断这项工作完成。复述用于暴露歧义，不默认要求用户逐句确认。
4. 分别记录原始反馈、已观察事实、已有决定、推测和未知。用户报告是调查输入；代码存在、文档声称和实际运行成功是不同证据。
5. 先确认最便宜的关键事实。文档与源码冲突时追踪对应版本和执行路径，不按文件名或更新时间自动选一个当真。

## 2. 按入口调查

| 入口 | 优先确定 | 可交付结果 |
| --- | --- | --- |
| 想法 | 受益对象、需要改变的行为、已有替代方式、约束 | 可观察目标、最小范围和有价值的未知 |
| 问题反馈 | 预期与实际、触发条件、影响范围、首次已知版本 | 复现、原因证据或明确的剩余假设 |
| 改进 | 同条件基线、目标指标、不能退化的行为 | 可对比的目标与验证条件 |
| 文档或契约漂移 | 声明对应的实现、适用版本、真实能力边界 | 可定位的差异及修正边界 |

不要把用户提出的解决办法直接当成根因。先检查它试图解决的实际问题，再判断是否需要其他方案。

## 3. 用有界调查消除不确定性

1. 只保留会改变后续行动的少量假设。对每个假设写出支持证据、反证条件和下一项最便宜的检查。
2. 选择能够区分假设的操作。定义环境、输入、观察点、预算和退出条件；先保存原始行为，再做隔离实验。
3. 优先检查实际操作面和失败路径。没有权限访问真实环境时，继续使用可用源码、历史和受控样本，并明确替代证据的限制。
4. 无新增信息时改变调查方法或停止。不要无限重复检索、堆日志或通过猜测性修复掩盖未知。
5. 同一事实被多个模型复述不增加证据强度。需要时让独立调查者读取原始材料，避免先提供预期结论。
6. 保留失败实验和无法复现的条件；一次未观察到故障不能推出故障不存在。

## 4. 形成结果契约

- 用稳定编号写出验收条件，描述可观察行为而非指定某个内部函数必须怎样实现。
- 分清当前问题、必须保持的行为、允许的变化和不在本次范围内的内容。
- 对并发、取消、重试、幂等、乱序、故障恢复等风险明确待回答的语义；只标记需要设计或建模的部分，不强制调用 TLA+。
- 为改进类任务记录测量条件、对照对象与退化边界；避免用不同负载或不同环境的结果计算提升。
- 记录设计需要解决的未知和实现可自行选择的细节。不要提前把每个细节都冻结为需求。
- 若事实表明原目标的前提不成立，给出具体差异及替代方向；不要静默换一个更容易完成的目标。

## 5. 只升级真正需要人的决定

先完成已有授权内的调查和可审查方案，再提出决定。

| 问题类型 | 默认动作 |
| --- | --- |
| 事实、接口现状、历史原因 | 查证并附来源 |
| 方案是否能运行、性能是否足够 | 做适当实验或交回可执行调查 |
| 已有边界内的常规实现选择 | 交给后续实现者自主处理 |
| 产品承诺、体验偏好、超出授权的成本或影响 | 提供具体决策卡 |

决策卡写明：要决定什么、为什么现在需要、推荐项、可行替代、依据、代价、影响的工作和等待后果。合并前提与权限范围相同的重复问题；不把其他项目的授权借到当前项目。

已有有效决定覆盖当前情境时直接复用。人的沉默不构成新授权，已查看摘要也不构成接受新目标。

## 6. 交接与停止

达到以下任一状态就结束本 Skill，并给出可执行下一步：

- **COMPLETE**：事实、范围和验收足以支撑下一项已约定工作；剩余非阻塞未知已经列出。
- **INCONCLUSIVE**：调查预算内仍无法支持关键结论；说明已排除什么、还缺什么、哪项检查最有价值。
- **BLOCKED**：缺少明确的访问、输入或人类决定；交出已完成工作，不伪报目标已完成。
- **NOT_RUN**：只完成了调查设计，实际检查尚未执行。

使用 `schema_version: work-result/v1` 交接：`work_id`、`skill`、`outcome`、`subject`、`evidence`、`unresolved`、`changed_assumptions`、`next_action`。

`subject` 至少包含 `kind` 与真实 `id`，按需补 `base_id`、`contract_id`、`environment_id`、`worktree_digest`。证据注明出处、版本、范围、状态与提供者；运行证据还要保留操作与结果。小任务可用等价紧凑文字，不强制新建大文档。

把业务修复交给实现，把方案取舍交给设计，把需要正式决策的事项交给既有决策路径。继续推进整项任务的责任留在外层调用者。

静态源码事实使用 `status: OBSERVED` 与 `kind: source_inspection`；引用旧实测使用 `HISTORICAL` 并保留其对象与日期。证据可记录 `id`、`locator`、`scope`、`status`、`producer`、`subject_id`，不把静态或历史证据标为当前实测 `PASS`。

JSON 交接时，next_action 与 evidence.scope 使用非空文本，结构化详情另放扩展字段；subject.id 使用含真实版本的不可变身份。引用不同对象的原始材料时保留原 subject_id 并标 relation=background，直接结论绑定当前对象；独立工具的原报告原样保留，由交接层包装，不要求它改用本格式。
