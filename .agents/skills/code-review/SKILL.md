# 双轴审查

## 适用场景

- 对某段 diff 或变更集执行双轴审查。
- 需要同时检查「实现是否符合项目规范」和「实现是否符合需求 / 来源 spec」。
- 若项目有平台化评审位或任务系统，按「可选：任务平台集成」执行。

## 项目适配

本技能默认使用 git 与常见的仓库文档约定；宿主项目有不同规范时，以宿主项目为准：

| 用途 | 默认约定 | 说明 |
| --- | --- | --- |
| 变更基准 | git commit、分支或 tag | 不使用 git 时，用等价的 diff 或文件快照 |
| 规范来源 | `CODING_STANDARDS.md`、`CONTRIBUTING.md`、`AGENTS.md` 等 | 没有文档时仍使用坏味道基线 |
| 来源 spec | 项目正式 spec（issue）、PRD 或任务描述 | 缺失时按第 2 步处理 |
| 任务平台 | issue tracker、任务系统或项目约定 | 用于读取任务上下文和写回报告，可选 |

## 输入

- 固定基准点（commit SHA、分支名、tag、`main`、`HEAD~5` 等）；未提供则先询问。
- 来源 spec：正式 spec 文件、issue/PRD 或任务描述；位置以项目约定为准。
- 仓库路径与规范来源（项目的编码规范、贡献指南或 agent 约定文件）。

## 流程

### 1. 固定基准点

用户指定的任何内容就是固定基准点。如果用户没有指定，就询问。

只记录一次 diff 命令：

```bash
git diff <fixed-point>...HEAD
```

使用三点，比较的是 merge-base。同时记录提交列表：

```bash
git log <fixed-point>..HEAD --oneline
```

继续之前，确认基准点可解析（`git rev-parse <fixed-point>`）且 diff 非空。无效 ref 或空 diff 必须在此处失败，不能进入两个并行子 agent。

如果项目不使用 git，改用等价的变更基准（如 PR diff、文件快照或发布包），并在报告中写明比较方式。

### 2. 确定来源 spec

按以下顺序查找：

1. 提交信息中的 issue 引用（`#123`、`Closes #45`、GitLab `!67` 等）。
2. 用户作为参数传入的路径。
3. issue/PRD 或任务描述中与分支名或功能匹配的内容。
4. 都不是时询问用户 spec 在哪里。

若 spec 位于 issue tracker，读取 issue 正文和已确认的变更记录；未确认的讨论不当作已批准需求。

优先使用 ticket 所属的已确认子 spec；没有子 spec 时使用已确认的主 spec（按项目约定识别：带 `needs-info` 的是草案，不带就绪标签的是已确认）。如果只有草案，可以把它作为需求参考，但必须在报告中注明「需求来源为草案，结论可能随 spec 变更」；不得把草案当作已批准的验收依据。子 spec 与主 spec 冲突时，以主 spec 的范围和验收为准，并在报告中记录冲突。需求轴优先引用需求 ID 和验收 ID，用 ticket 的覆盖映射定位实现范围。

缺少 spec 时，跳过需求轴并注明「无可用 spec」。若任务明确要求以任务描述为 spec，而描述为空，则视为不可评审，按失败处理，不伪造结论。

### 3. 确定规范来源

查找仓库中说明代码应如何编写的文档，例如 `CODING_STANDARDS.md`、`CONTRIBUTING.md` 或 agent 约定文件。

除仓库文档外，标准轴始终携带下面的**坏味道基线**——一组固定的 Fowler 代码坏味道（《重构》第 3 章），即使仓库没有任何文档也适用：

- **仓库优先**：仓库文档化的标准始终优先；如果某个标准认可基线会标记的做法，就抑制该坏味道。
- **始终是判断**：每个坏味道都是带标签的启发式判断（例如「可能的依恋情结」），绝不是硬性违规；跳过工具已经强制执行的项。

每个坏味道按「是什么 → 如何修复」阅读，对照 diff 匹配：

- **神秘命名（Mysterious Name）**——函数、变量或类型的名字不能揭示它做什么或保存什么。→ 重命名；如果找不到诚实的名字，说明设计有问题。
- **重复代码（Duplicated Code）**——相同的逻辑形态在变更中的多个 hunk 或文件中出现。→ 抽取共享形态，让两处调用。
- **依恋情结（Feature Envy）**——方法访问另一个对象的数据多于自己的数据。→ 把方法移到它依恋的数据上。
- **数据泥团（Data Clumps）**——同一组字段或参数总是结伴出现（一个类型在呼唤诞生）。→ 捆绑成一个类型并传递它。
- **基本类型偏执（Primitive Obsession）**——用基本类型或字符串代替值得拥有自己类型的领域概念。→ 给该概念一个小的专属类型。
- **重复的 switch（Repeated Switches）**——同一个 `switch`/`if` 级联在变更中反复出现。→ 用多态或共享映射替代。
- **霰弹式修改（Shotgun Surgery）**——一次逻辑变更迫使跨多个文件分散编辑。→ 把一起变化的内容聚集到一个模块。
- **发散式变化（Divergent Change）**——一个文件或模块因几个不相关的原因被编辑。→ 拆分，使每个模块只因一个原因变化。
- **夸夸其谈通用性（Speculative Generality）**——为 spec 没有的需求添加抽象、参数或钩子。→ 删除；内联回退，直到真实需求出现。
- **过长的消息链（Message Chains）**——调用方不应依赖的 `a.b().c().d()` 长导航。→ 在第一个对象上用一个方法隐藏整个遍历。
- **中间人（Middle Man）**——主要只是转发调用的类或函数。→ 删除，直接调用真实目标。
- **被拒绝的遗赠（Refused Bequest）**——子类或实现者忽略或覆盖了继承来的大部分内容。→ 放弃继承，改用组合。

### 4. 并行启动两个子 agent

发送一条包含两个子 agent 调用的消息（如 Claude Code 的 `Agent` 工具）。两个都使用宿主提供的通用子 agent（如 `general-purpose`）。若宿主不支持子 agent，则分两次独立执行，保持两轴上下文分离，不要合并成一次审查。

**标准轴子 agent 提示词**——包含：

- 完整的 diff 命令和提交列表。
- 第 3 步找到的规范来源文件列表，**以及坏味道基线全文**——子 agent 没有其他途径获取它。
- 简报：「按文件/hunk 报告：(a) diff 违反文档化标准的每一处，引用标准（文件 + 规则）；(b) 发现的任何基线坏味道，命名并引用 hunk。区分硬性违规与判断性意见——文档化标准的违规可以是硬性的，但基线坏味道始终是判断性意见，且仓库文档化标准优先于基线。跳过工具已经强制执行的项。不超过 400 字。」

**需求轴子 agent 提示词**——包含：

- diff 命令和提交列表。
- spec 的路径或获取到的内容。
- 简报：「报告：(a) spec 要求但缺失或部分实现的需求；(b) diff 中未被要求的行为（范围蔓延）；(c) 看起来已实现但实现错误的需求。每个发现引用对应的需求/验收 ID 和 spec 原文。不超过 400 字。」

缺少 spec 时，按第 2 步的规则跳过或失败。

### 5. 汇总与结论

在 `## 标准轴` 和 `## 需求轴` 标题下分别呈现两份报告，可逐字或轻度清理。**不要**合并或重新排序发现——两个轴是刻意分开的（见「为什么分两轴」）。

最后写一行总结：每个轴的发现总数，以及每个轴内最严重的问题（如果有）。不要跨轴选出一个总冠军——这正是分轴要避免的重新排序。

## 可选：任务平台集成

如果项目使用任务/评审平台：

1. 把两份报告与总结写入任务或 PR 评论；PR 正文由 `pr` 生成，只放结论和报告位置，不重复报告全文。
2. 评审人给出通过/打回结论：
   - 标准轴无硬性违规，且需求轴无缺失、错误实现或范围蔓延 → 通过。
   - 否则打回，并附必须修复的项。
3. 项目约定的管理者可覆盖评审结论。
4. 记录 fixed point、提交范围、宿主/工具版本与命令，保证可追溯。

## 与其他技能的关系

- `implement` / `implement-spec`：实现完成后调用本技能；被打回时回到对应 ticket 修复。
- `tdd`：测试由它产出；本技能判断测试是否在已确认的 seam 上、是否与实现耦合。
- `pr`：读取本技能的结论生成 PR 描述；报告全文留在评论中，不复制进 PR 正文。
- `to-spec` / `to-tickets`：提供需求轴所需的 spec、需求 ID 和验收映射。

## 复用

本技能无额外文件依赖；复制 `SKILL.md` 到目标项目的技能目录即可。

## 为什么分两轴

一个变更可以通过一个轴而失败于另一个轴：

- 代码遵循所有标准但实现了错误的东西 → **标准轴通过，需求轴失败。**
- 代码完全实现了 issue 要求但破坏了项目惯例 → **需求轴通过，标准轴失败。**

分开报告可以防止一个轴掩盖另一个轴。
